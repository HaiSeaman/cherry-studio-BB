**构建期抓到的坑（单测发现不了，靠真跑一次构建才看到）**

⚠️ 剩下唯一无法在无界面环境验证的：Electron 里 `file://` 同源加载 worklet 模块本身（回退路径保证最坏情况=修复前）。

## 零、一句话结论

主人感觉到的"卡"，**不是网络慢，是这台电脑的界面线程被自己堵住了**：
录音用的是一个早就被官方废弃、把音频处理压在"界面主线程"上的老接口；同时每打一个字都要让输入框做 2 次以上的"强制重新排版"，一次识别结果吐几个字就把界面堵成一片。
"光标输入不对劲"的元凶是 **按住 Ctrl 说话时，代码注入的"退格键"在目标程序里被当成了「Ctrl+退格 = 删一整个词」**，而打字器却按"删一个字"来算账，一错就整段崩。
"API 传输不对劲"里有一条**硬伤**：腾讯那家的结束报文写错了，官方要 `{"type": "end"}`，代码发的是 `{"end": true}`。

## 二、卡顿：三条原因叠在一起，还会互相放大

### A1. 录音接口是被官方废弃的老 API，音频处理压在界面主线程 【官证】

- 位置：`src/renderer/src/hooks/useVoiceInput.ts:75`（`createScriptProcessor(4096, 1, 1)`）、`:79`（`onaudioprocess`）
- 官方原文（Chrome Web Audio 团队）：`ScriptProcessorNode` **"used event handlers to invoke user script in the main UI thread … the event handling is asynchronous by design, and the code execution happens on the main thread. The former induces the latency, and the latter pressures the main thread … causing either UI to "jank" or audio to "glitch". Because of this fundamental design flaw, ScriptProcessorNode is deprecated"`。
  翻译成人话：**它把"录到的声音打包"这件事交给画界面的那根线程去做**。界面一忙，打包就迟到 → 界面更卡、声音还掉块。
- 替代方案是 `AudioWorklet`：它的处理函数跑在**音频专用线程**，"零额外延迟、同步渲染"，界面再忙也不影响录音。
- 为什么当初会用老接口：它是"零配置就能跑"的写法，不需要单独写一个 worklet 文件。
- 收益（换掉之后）：录音不再受界面卡顿影响，掉音消失。
- 风险：AudioWorklet 要求把处理代码放进一个独立文件、用 `addModule()` 加载；Electron 打包时要确认该文件被正确打进产物（走 Vite 的 `?worker&url` 或 `new URL(...)` 方式），否则线上会"加载不到处理器"。

### A2. 每打一个字，输入框都要"强制重新排版" 【实测】

- 位置：`src/renderer/src/pages/home/Inputbar/components/InputbarCore.tsx:652-677` 的受控 `<Textarea>`，`autoSize={{minRows:2,maxRows:20}}`（`:665`）
- 机制（读 `node_modules/.pnpm/rc-textarea@1.10.2/.../es/ResizableTextArea.js:84-113` 与 `.../calculateNodeHeight.js:17,70,74,84`）：只要 `value` 变一次，组件就走三步 `setState`，最后调 `calculateAutoSizeStyle()` —— 里面要 `window.getComputedStyle()`、把一大串样式写到一个隐藏 textarea 上、**读两次 `scrollHeight`**。读 `scrollHeight` 会逼浏览器立刻把整个文档重新排版（这叫"强制同步重排"，最贵的操作之一）。
- 实测数字（探针 C）：每注入 1 个字符 ≈ `getComputedStyle` **1.4 次**、`scrollHeight` **2.4 次**、外层组件重渲染 **1.2 次**；真机上外层重渲染的是整棵 Inputbar（工具栏、Token 计数、翻译按钮、快捷面板全在里面），比我的最小复现重得多。
- 放大效应（这就是"死循环"）：语音打字 → 界面忙着重排 → A1 的音频回调被挤掉 → 音频掉块 → 识别变差 → 服务端改写 → 更多退格重打 → 界面更忙。**越说越卡，卡了识别就更差。**

### A3. 主进程每 500 毫秒给剪贴板图片做一次 PNG 编码 + MD5 【已核对代码】

- 位置：`src/main/services/ClipboardService.ts:73`（`setInterval(poll, 500)`，`init()` 在 `src/main/index.ts:216` **无条件**启动）、`:114-121`（只要剪贴板有图片就 `readImage()` → `toPNG()` → `md5`）
- 致命细节：用来"省钱"的变化闸门 `cheap !== this.lastCheapKey` 在 `:201`，**排在昂贵计算之后**——等于白算。代码里自己都留了注释承认"图片指纹每轮重算…实测 CPU 偏高"。
- 为什么牵连语音：主进程同时也是**音频转发**（`src/main/ipc.ts:610-612`）和 **SendInput 注入按键**（`src/main/services/voiceInput/textInserter.ts:87-103`）的执行者。主进程一卡，这两件事一起顿。
- 触发条件：**只要主人复制过一次图片**，之后一直有效。可以拿这个验证：复制一张图，再说话，是否更卡。

### A4. 每句话开头的 0.1~0.5 秒根本没录到 【推断，需真机对拍】

- 位置：`useVoiceInput.ts:65`（`getUserMedia`）与 `:73`（`new AudioContext()`）都在**收到"按下"事件之后**才开始，全仓只有这一处调用（没有预热、没有常开）。
- 时间线：按下 → 20ms 防抖 → 通知渲染进程 → 现开麦克风 → 现建音频上下文 → 等第一块音频（85ms）→ 才推给云端。社区大规模实测数据：已授权后 `getUserMedia` **45% <100ms、75% <500ms**。
- 表现："我明明说了，前面几个字没了"，而且越短的词越明显（短词可能整句丢）。
- 顺带：`src/renderer/src/hooks/useVoiceInput.ts:123-127` 对状态广播**只处理了 `error`**，录音中/正在上屏**没有任何界面提示**。主人不知道"现在可以开口了"，体感就更卡。

## 三、光标输入"不对劲"：最要命的一条

### B1. 按住 Ctrl 说话时，注入的"退格"其实是「Ctrl+退格 = 删一个词」 【实测 + 官证，最高优先级】

证据链（每一环都可查）：

1. **默认快捷键就是 `Ctrl + \``**：`packages/shared/config/constant.ts:244`。而"按住说话"意味着**整个录音期间 Ctrl 一直是物理按下的**。
2. **退格是"真按键"**：`src/main/services/voiceInput/textInserter.ts:52-60` 注入真 `VK_BACK`（0x08）。
3. **微软官方文档原文**（SendInput）：`"This function does not reset the keyboard's current state. Any keys that are already pressed when the function is called might interfere with the events that this function generates."` —— 官方明确承认"调用时按住的键会干扰注入按键的语义"。
4. **Chromium 读修饰键用的是全局按键状态**（`ui/events/win/events_win_utils.cc` 的 `GetModifiersFromKeyState()`，含 `IsCtrlPressed()`），所以注入的 VK_BACK 带着 `ctrlKey = true` 到达网页 —— 就是一次真正的 **Ctrl+Backspace**。
5. **Blink 里 Ctrl+Backspace = `deleteWordBackward`（按词向前删）**：官方级证据是 Blink 自己的测试源码 `inputevent-keyboard.html` 里 `const DELETE_WORD_MODIFIER = isMacOS ? 'altKey' : 'ctrlKey'; … testKeyDownInputType('Backspace', [DELETE_WORD_MODIFIER], 'deleteWordBackward')`。
6. **而打字器是按"1 次退格 = 删 1 个字符"算账的**：`src/main/services/voiceInput/streamingTypewriter.ts:65-72`（`removeCount` 按码点计数）。
7. **实测（探针 A）**：让打字器把 `hello world` 改写成 `hello there`，它算出"退格 5 次"，目标框实际**把整段 `hello world` 删光**，最后只剩下 `there`；而且打字器自己记的还是 `hello there` —— **它以为打对了，其实已经错位，这一轮剩下的内容全部跟着错。**

为什么主人会"觉得不对劲但说不清"：

- **纯中文时看着正常**：ICU 的分词规则把每个汉字当一个"词"，所以 Ctrl+退格 ≈ 普通退格，运气好。实测（探针 A 第二条）中文改写结果正确。
- **一旦出现英文、数字、中英混排就吞字**：`199 元`、`hello`、`abc123` 这类会被整段吃掉。
- 代码注释里其实**只想了一半**：`textInserter.ts:31-35` 与 `docs/wiki/03-主进程模块.md:96` 都写着"字符走 WM_CHAR 通道，不受物理按住的修饰键影响"——**管住了"打字符"，没管住"按退格"**。

风险提示（这条也关系到怎么修）：**"临时松开 Ctrl 再按回去"这种修法有坑**。`pressHoldDetector`（`pressHoldDetector.ts:77-95`）和 `focusGuard` 的 keyup 处理**完全没有"辨别自己注入回声"的能力**——注入一个 Ctrl 抬起事件，按住说话会立刻被判成"松手"，录音当场停止。所以修之前必须先给 keyup 补回声抑制。

### B2. 焦点守卫用"120 毫秒时间窗"猜哪个按键是自己打的 【实测】

- 位置：`src/main/services/voiceInput/focusGuard.ts:6`（`INJECTION_ECHO_MS = 120`）、`:13-15`（`isUserInputEvent`）。
- 逻辑是"最近 120ms 内注入过，就当我自己的回声，不算主人操作"。但这只是**时间上的猜**，不是可靠判据。
- 实测（探针 B）：晚到 100ms → 判为回声（对）；晚到 **130ms → 判成"主人在按键"**。
- 后果放大：一旦误判就调用 `typewriter.freeze()`，之后**只允许追加、禁止退格**；若服务端此时改写了前文，`commit()` 直接 `return`（`streamingTypewriter.ts:58-63`），于是**最终文本一个字都打不进去**（探针 B 第二条实测：光标处停在旧的中途结果）。这不是"少几个字"，是整段校正静默丢失。
- 按 A1/A2/A3 的现实情况（界面忙、主进程忙）注入晚到超过 120ms 一点都不稀奇。

### B3. 快速连按 → 麦克风泄漏 + 双路串音 【实测】

- 位置：`useVoiceInput.ts:56`（`captureRef`）、`:58`（`stoppedRef`）、`:60-72`。
- `stoppedRef` 只是一个**布尔开关**，不是"这是第几轮"的编号。当 `begin → end → begin` 全都落在"`getUserMedia` 还没返回"的窗口里（约 100~500ms，见 A4）时：第 2 次 `begin` 把 `stoppedRef` 重置为 `false`，于是**第一次那路麦克风也醒过来建链路**。
- 实测（探针 E）：录音链路数 = **2**（应为 1）、第 1 路麦克风 `stop` 调用 **0 次**（永不释放）、`sendAudio` 被调用 **2 次**（同一路音频推了两份）。
- 后果：① 麦克风指示灯一直亮着（隐私上很难看）；② 每次误触就多留一条常驻音频链路 → **CPU 越用越高，越用越卡**（这条正好解释"用久了更卡"）；③ 同一句话被推两份，识别结果被污染。
- 收益（修好之后）：麦克风一定能释放、不会越用越卡、没有双份音频。
- 风险：修法是给每一轮录音加一个"轮次号"，在异步返回后核对；要注意别把"真的新一轮"也误判掉（新轮次号必须由 `begin` 事件生成，不能在 `startCapture` 内部生成）。

### B4. 没有任何"我打进去的字还在不在光标左边"的确认机制 【推断，属设计脆弱性】

打字器（`streamingTypewriter.ts`）靠"我记得我打了什么"来算退格数量。只要有一次注入被目标程序吞掉（提权窗口、被别的软件拦截、输入法抢占），它记的账就和现实永久对不上，而且**整段录音期间都没有任何重新同步的机会**。目前 `textInserter.ts:96-98` 只在 `SendInput` 返回值不等时打一行日志，**打字器照样更新自己的记录** —— 等于明知失败还记账。

### B5. 关联但独立的小隐患：输入框本身的两个问题 【已核对代码】

- `src/renderer/src/pages/home/Chat.tsx:184` 给 `<Messages>` 加了 `key={topic.id}`（话题切换重挂载），紧邻的 `:199` `<Inputbar>` **没有 key** → 切换话题时输入框内容不换，而且草稿缓存键是全局唯一一个（`Inputbar.tsx:50,132-135`）→ **所有话题共用一份草稿，有把内容发到错误会话的风险**。这与语音无关，但同属"输入框手感"。
- `src/renderer/src/hooks/useTextareaResize.ts:73-77`：先写 `style.height='auto'` 再立刻读 `scrollHeight`，每次调整都强制重排一次（和 A2 同源）。

## 四、API 数据传输：一条硬伤 + 几条可靠性缺口

### C1. 腾讯：结束报文写错，服务端会报 4010 并直接断连 【官证，我独立抓了原文】

官方页面（cloud.tencent.com/document/product/1093/48982，「识别阶段 → 上传数据」）原文：

> 音频流上传完成之后，客户端需发送以下内容的 text message，通知后台结束识别。
> `{"type": "end"}`

错误码表里还有一条 `4010 客户端上传未知文本消息` —— 说明这个文本帧的内容被**严格校验**。

而代码发的是 `{"end": true}`：`src/main/services/voiceInput/asr/tencent.ts:130-132`；**单测还把这个错值锁死了**：`asr/__tests__/tencentProtocol.test.ts:92`（`expect(buildTencentEndMessage()).toBe('{"end":true}')`）→ 所以测试全绿也照样是坏的。

后果链条：
1. 服务端不认识这条消息 → 回 `code=4010` 并断开（收不到 `final: 1`）。
2. 代码 `tencent.ts:239-247` 走 `code !== 0` 分支 → `onError` → 主人看到**假警报**"语音识别出错：请检查识别服务密钥与网络"（密钥明明是对的）。
3. `finalize` 只能等 5 秒超时兜底（`tencent.ts:135`）→ **每次松手都要多等最多 5 秒**，"最后一句"才可能有校正。
4. `handleMessage` 里 `resolve` 用的是 `this.resultText`，而它**只累积"稳态"（slice_type=2）文本**（`tencent.ts:249-258`）。松手时最后一句往往还没稳态 → **已经上屏的最后一句会被回滚删掉**（`StreamingTypewriter.commit` 会把分叉的尾巴退格删掉）。

### C2. 腾讯：音频包大小与官方推荐不一致 【官证】

官方建议 16k 采样率 **200ms / 6400 字节**一包（1:1 实时率）；代码统一发 **100ms / 3200 字节**（`useVoiceInput.ts:8`）。
不违规（速率仍是 1:1），但和官方推荐值不一致；官方也明确"过快超过 1:1 或包间隔超过 6 秒"才会出错。**优先级：低**，属于可调优项。

### C3. 千问：收尾逻辑是对的，但"task-finished 一定会回来"官方从没承诺 【官证】

- 官方明确："发出 `finish-task` 之后仍会继续收到 `result-generated`（最后一句的最终结果），然后才是 `task-finished`"。代码这条**做对了**（`asr/qwen.ts:240-242` 只在收到 `task-finished` 时才 resolve）。
- 但官方**从未用"一定/保证"措辞**，失败路径单列为 `task-failed`（连接直接关闭、不可复用）。现在只有 5 秒超时兜底（`qwen.ts:95,202`），超时后返回的是当时已有的文本 → 最后一句可能不校正。
- 建议：超时兜底时改用"最后一条 `sentence_end=true` 的结果"（那本身就是官方定义的最终结果），并打一条告警日志。

### C4. 千问：没开保活，长静音会断 【官证】

- 官方在 `run-task` 的 `parameters` 里有 `heartbeat`（默认 `false`），语义是"**在持续发送静音音频的情况下**保持连接不中断"。代码的 `buildRunTaskMessage`（`asr/qwen.ts:12-24`）没带这个参数，也**不会主动补发静音包**（`useVoiceInput.ts:79-88` 只有真实音频才发块）。
- 后果：说长句中间停顿久了可能被服务端超时断连（官方案例里出现过 `request timeout after 23 seconds`），整轮白说。
- 风险：补静音包要小心别让服务端把静音当语音识别出内容；建议用全 0 的 PCM 并在 URL/参数上开 `heartbeat`。

### C5. 豆包：核对下来**没问题**，不用改（避免白折腾）

- 末包帧 `[0x11, 0x22, 0x00, 0x00]`（`asr/doubao.ts:27-28`）→ message type `0b0010`（audio only）+ flags `0b0010`（最后一包、不带 sequence），**与官方示例完全一致**。（网上流传的 `0b0011` 是"带负 sequence 的末包"，若用 `0b0011` 就必须补 4 字节负 sequence，代码没用错的那套。）
- `X-Api-Key`、`X-Api-Resource-Id`、`X-Api-Request-Id`、`X-Api-Sequence: -1`（`asr/doubao.ts:146-154`）**都在官方文档里**（`X-Api-Sequence` 固定 -1 是 HTTP 握手头，别和二进制帧里的 sequence 混）。
- `result_type` 官方默认就是 `full`（累计全量）→ 代码"整段覆盖"的用法（`asr/doubao.ts:252-258`）正确。
- **可调优点（都不算错）**：① 官方说双向流式 **200ms 分包性能最优**，现在发 100ms；② 没配 `end_window_size`（默认 800ms 静音判停）→ 松手后最多要等 800ms 才出最终句，调小到 200~300 会更跟手（代价：断句更碎）。

### C6. 录音数据本身被削了：降采样没有抗混叠滤波 【实测】

- 位置：`useVoiceInput.ts:16-33`（`resampleTo16k`，48k→16k 只是"每 3 个样本取平均"）。
- 实测（探针 D）：1kHz 剩 98.6%（-0.1dB）、3kHz 剩 94.9%（-0.5dB）、6kHz 剩 **80.5%（-1.9dB）**；更严重的是**超过 8kHz 奈奎斯特的 10kHz 分量没有被滤掉，还有 48.9%（-6.2dB）混叠折叠回可听频段**。
- 人话：等于把声音"变闷"（齿音、辅音变糊）再掺一层假的低频镜像音，然后才交给识别引擎。识别引擎本来就靠辅音分辨字，这会直接拉低准确率 → 触发更多改写 → 又回到 A2 的卡顿循环。
- 收益（修好之后）：同样说一句话，识别更准，改写更少，界面更少重排。
- 风险：换成正经抗混叠滤波器（或直接让 `AudioContext` 以 16k 采样率创建，让浏览器自己做这件事）会略微增加一点 CPU，但相比 A1 的收益可以忽略。**注意：`sampleRate: 16000` 创建 AudioContext 在部分 Windows 声卡驱动上可能不被支持，需要回退到 48k + 自己滤波。**
