## A. 腾讯云实时语音识别 WebSocket

官方页面：https://cloud.tencent.com/document/product/1093/48982
（页面标注「最近更新时间：2026-08-04 11:50:08」）

### A1. 音频发送完毕、通知服务端结束识别的确切消息格式

**结论：官方要求 `{"type": "end"}`。不是 `{"end": true}`。置信度：高（官方原文直接证实）。**

官方原文（识别阶段 → 上传数据）：

> 音频流上传完成之后，客户端需发送以下内容的 text message，通知后台结束识别。
> ```bash
> {"type": "end"}
> ```

补充要点（同样来自官方原文）：
- 该消息是 **text message**（文本帧），不是 binary 帧。
- 音频数据本身必须用 **binary message** 持续上传。
- 错误码表里有一条相关条目：`4010 客户端上传未知文本消息。` —— 说明结束消息的文本内容被服务端严格校验，写错会报 4010。

**为什么重要**：很多实现照抄别家协议写成 `{"end": true}` 或 `{"type":"finish"}`，会直接触发 4010 或一直不收尾。这一点官方文档写得非常明确，不用猜。

### A2. 音频包的发送节奏 / 包大小硬性要求

**结论：官方"建议"（不是"H 必须"）200ms 一包、1:1 实时率；过快或间隔过久都会报错并断连。置信度：高。**

官方原文（接口要求表 → 数据发送 一栏，两处表述一致）：

> 建议200ms 发送200ms 时长（即1:1实时率）的数据包，对应 PCM 大小为：8k 采样率3200字节，16k 采样率6400字节。音频发送速率过快超过1:1实时率或者音频数据包之间发送间隔超过6秒，可能导致引擎出错，后台将返回错误并主动断开连接。

注意用词是**"建议"**——这属于推荐值，不是协议硬校验；但违反的后果官方明确说了：报错 + 主动断开。

官方错误码表原文（音频节奏相关的两条）：

| 错误码 | 官方说明原文 |
| --- | --- |
| 4000 | 音频数据发送过多，请1秒内最多发送3秒音频数据。注意：实时识别的效果是"边说边出文字"，1秒内发送的音频数据总时长应为1秒。 |
| 4008 | 客户端超过15秒未发送音频数据。 |

> ⚠️ 提醒一处**官方文档自身不一致**：正文说"包之间间隔超过6秒"会出错，而错误码表写的是"超过15秒未发送音频数据"报 4008。两个数字不冲突（一个是引擎保护、一个是等待超时），但如果代码里靠"6~15 秒区间"保活，会踩坑。置信度：高（两处原文都在同一页面）。

**给主人的大白话**：发包节奏要跟"真人说话的语速"对齐。提前把 10 秒音频瞬间灌进去 = 4000 报错；中途停手超过 6 秒 = 可能被断开；超过 15 秒不发 = 一定 4008。

### A3. `engine_model_type` 取值差别；哪个适合「按住说话、边说边出字」

**结论：**
- **`16k_zh`**：通用中文引擎（页面归在"通用引擎"组），示例值就是它。置信度：高。
- **`16k_zh_en`**：中英大模型引擎【大模型1.0版】，支持中/英/粤+31 种方言，对噪声大、回音大、人声小、人声远等低质量音频准确率提升。置信度：高。
- **`16k_zh_large`：在 48982 这页里不存在（查无此引擎）。** 该页里的"large"只有 `8k_zh_large`（中文电话场景专用大模型引擎【大模型1.0版】）和 `16k_en_large`（英文大模型引擎【大模型1.0版】）。置信度：高（对 48982 页面而言）。
- **`16k_zh_en_2.0`：在 48982 这页里也不存在**，但它**确实存在**——在**实时语音识别 V2（WebSocket）**页面（https://cloud.tencent.com/document/product/1093/131127 ）里，官方原文：

> 16k_zh_en_2.0：中英粤+30种方言大模型引擎【大模型2.0版】。该模型同时支持中文、英语、粤语、四川话、陕西话、河南话、上海话、湖南话、湖北话、安徽话、闽南话、潮汕话等 31种方言 的识别……示例值：16k_zh_en_2.0

同一 V2 页面还有 `16k_zh_en_speaker_2.0`（额外支持说话人分离）。

**所以关键区分（这是最容易搞错的地方）：**
1. `16k_zh_en_2.0` 属于 **V2 接口（/asr/v2/...）的引擎体系**，不在 48982 老页面的引擎列表里。两个页面的引擎列表不能混用。
2. 48982 页面新增的 **大模型2.0版**引擎是 `Hy-ASR-3.0-preview`，但官方明确标注它的限制：

> 当前为 Preview 版本，部分功能暂不支持。如：仅支持60秒以内的语音输入；仅支持16k 单声道 PCM 音频格式输入。

**哪个适合"按住说话、边说边出字"？**
- 官方对 48982 这个接口的整体定位就是"边说边出文字"：

> 本接口服务采用 WebSocket 协议，对实时音频流进行识别，同步返回识别结果，达到"边说边出文字"的效果。

- 因此**能不能"边说边出字"是接口决定的，不是引擎决定的**——48982 接口下的所有引擎都返回中间结果（见 A4）。
- 选型建议（**判断，非官方结论**）：要中文实时输入法式体验，`16k_zh`（通用、便宜、稳）够用；要抗噪/方言/中英混说，用 `16k_zh_en`；要最新 2.0 大模型，得换到 V2 接口文档（131127）并按它的参数体系走。**不要**在 48982 里填 `16k_zh_en_2.0`（该页未列出），也不要盲目用 `Hy-ASR-3.0-preview`（有 60 秒上限的官方限制）。

### A4. 是否支持中间结果（slice_type 0/1）与稳态结果（slice_type 2）；`final: 1` 含义

**结论：全都支持，且官方给出原文定义。置信度：高。**

官方原文（Result 结构体 → slice_type）：

> 识别结果类型：
> 0：一段话开始识别。
> 1：一段话识别中，voice_text_str 为非稳态结果（该段识别结果还可能变化）。
> 2：一段话识别结束，voice_text_str 为稳态结果（该段识别结果不再变化）。
> 根据发送的音频情况，识别过程中可能返回的 slice_type 序列有：
> 0-1-2：一段话开始识别、识别中（可能有多次1返回）、识别结束。
> 0-2：一段话开始识别、识别结束。
> 2：直接返回一段话完整的识别结果。
> 注意：如果需要0和2配对返回，需要设置 filter_empty_result=0（slice_type=0时，识别结果可能为空，默认是不返回空识别结果的）。

官方原文（`final` 字段）：

> final：该字段返回1时表示音频流全部识别结束。

官方原文（终帧示例与副作用）：

> 后台识别完所有上传的语音数据之后，最终返回 final 值为1的消息并断开连接。
> ```bash
> {"code":0,"message":"success","voice_id":"CzhjnqBkv8lk5pRUxhpX","message_id":"CzhjnqBkv8lk5pRUxhpX_241","final":1}
> ```

**实操要点（推导，非官方原文）**：
- `final: 1` 这一帧**没有 result 字段**，只是"全流识别完毕"的终止信号，随后服务端主动断开。所以代码里不能把 `final:1` 当"最后一句话的结果"来取文本。
- 想拿到"配对"的句子边界（0 开头、2 收尾），必须显式传 `filter_empty_result=0`，否则空的不稳态结果默认被吞掉。
- 另外两个有用的官方参数：`needvad`（默认0，开启人声切分）、`vad_silence_time`（500–2000ms，默认1000）、`max_speak_time`（5000–90000ms，默认60000，超时会强制断句并把结果变成稳态 slice_type=2）。

### B2. 二进制帧头 4 字节的确切定义；音频帧的 message type 与 flags；末包 flags 到底是 `0b0010` 还是 `0b0011`

**结论（官方字节表逐字段，置信度：高）：**

官方原文（header 数据格式，Byte\Bit 0–7）：

| Byte \ Bit | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | Protocol version | | | | Header size | | | |
| 1 | Message type | | | | Message type specific flags | | | |
| 2 | Message serialization method | | | | Message compression | | | |
| 3 | Reserved | | | | | | | |

官方字段取值表原文：

| 字段 (size in bits) | 官方值 |
| --- | --- |
| Protocol version (4) | `0b0001` - version 1 (目前只有该版本) |
| Header (4) | `0b0001` - header size = 4 (1 x 4)。实际 header 大小（以字节为单位）是 header size value x 4 |
| Message type (4) | `0b0001` 端上发送包含请求参数的 full client request；`0b0010` 端上发送包含音频数据的 audio only request；`0b1001` 服务端下发包含识别结果的 full server response；`0b1111` 服务端处理错误时下发的消息类型 |
| Message type specific flags (4) | `0b0000` header后4个字节不为sequence number；`0b0001` header后4个字节为sequence number且为正；`0b0010` header后4个字节不为sequence number，仅指示此为最后一包（负包）；`0b0011` header后4个字节为sequence number且需要为负数（最后一包/负包） |
| Message serialization method (4) | `0b0000` 无序列化；`0b0001` JSON 格式 |
| Message Compression (4) | `0b0000` no compression；`0b0001` Gzip 压缩 |
| Reserved (8) | 保留以供将来使用，还用作填充（使整个标头总计4个字节） |

**音频帧（audio only request）的官方示例取值：**
- **普通音频包**：message type `0b0010`，message type specific flags **`0b0000`**（"用户设置正数 sequence number"），serialization `0b0000`（none - raw bytes），compression `0b0001`（Gzip）。
- **末包音频**：官方 Message flow 示例原文：

> client 发送包含最后一包音频数据（通过 message type specific flags) 的 "Audio-only client request"，
> message type:`b0010`(audio only client request) message type specific flags:**`b0010`**(最后一包音频请求) message serialization method:`b0000`(none - raw bytes) message compression:`b0001`(Gzip) reserved data:`0x00`

**→ 末包 flags 官方示例是 `0b0010`，不是 `0b0011`。**

**那 `0b0011` 是什么？** 它是**协议合法的另一种末包写法**：官方字段表写明 `0b0011` = "header后4个字节为sequence number且需要为负数"。官方示例里 `0b0011` 出现在**服务端响应的终帧**（`message type:0b1001`、`flags:0b0011`、且带 4 字节 sequence），**不是**客户端发的音频帧。

**社区实现证据（明确标注为社区/非官方，用于说明两种都可能被接受）：**
- 火山官方开源仓库（volcengine/veadk-python，github.com/volcengine/veadk-python）`asr_client.py` 中：

```python
class MessageTypeSpecificFlags:
    NO_SEQUENCE = 0b0000
    POS_SEQUENCE = 0b0001
    NEG_SEQUENCE = 0b0010
    NEG_WITH_SEQUENCE = 0b0011

@staticmethod
def new_audio_only_request(seq, segment, is_last=False):
    header = AsrRequestHeader.default_header()
    if is_last:            # 最后一个包特殊处理
        header.with_message_type_specific_flags(
            MessageTypeSpecificFlags.NEG_WITH_SEQUENCE)   # = 0b0011
        seq = -seq                                     # 设为负值
```

  即**该官方仓库采用 `0b0011` + 负 sequence**（同时全程给普通包带正 sequence `0b0001`）。
- 另一个第三方实现（TEN-framework/ten-framework）则严格照文档走：

```python
if is_last:
    # According to ByteDance documentation, last packet uses specific flag
    header.with_message_type_specific_flags(MESSAGE_TYPE_SPECIFIC_FLAGS_LAST_AUDIO)  # 0b0010
    # Last packet doesn't need sequence number, use 0
    seq = 0
```
  并注明 "Only non-last packets include sequence number"。

**给主人的结论（可直接落地）：**
- **照官方文档走最稳**：普通音频包 `0b0010 + 0b0000`；末包 `0b0010 + 0b0010`（不带 sequence）。
- 如果代码已经写成 `0b0011` + 负 sequence，**也不一定错**（官方开源仓库就这么干），但**必须保证"带负号 4 字节 sequence"和 flags `0b0011` 同时出现**——`0b0011` 却不带 sequence 字段是协议违规。
- 最常见的坑：普通包用 `0b0001`（声称有正 sequence）却忘了在 header 后写 4 字节 sequence，导致服务端把 payload 长度字段错位解析。

### B3. full client request（首帧）JSON payload 必填字段；`model_name` 填什么；是否必须 `result_type`；默认值

### B4. 双向流式 vs 单向流式；官方推荐包长；VAD 参数与默认值

> 双向流式模式使用的接口地址是 wss://openspeech.bytedance.com/api/v3/sauc/bigmodel
> 流式输入模式使用的接口地址是 wss://…（即 `bigmodel_nostream`）
> 1. 两者都是每输入一个包返回一个包，双向流式模式会尽快返回识别到的字符，速度较快。
> 2. 流式输入模式会在输入音频大于15s或发送最后一包（负包）后返回识别到的结果，准确率更高。
> 3. 无论是哪种模式，单包音频大小建议在100~200ms左右，发包间隔建议100～200ms，不能过大或者过小，否则均会影响性能。（注：针对双向流式模式，单包为200ms大小时性能最优，建议双向流式模式选取200ms大小的分包）
> 4. 流式输入模式在平均音频时长5s时，可以做到300~400ms以内返回。
>
> 双向流式模式（优化版本）接口地址：wss://…（另有优化版地址）
> 1. 该模式下，不再是每一包输入对应一包返回，只有当结果有变化时才会返回新的数据包（性能优化 rtf 和首字、尾字时延均有一定程度提升）
> 2. 双向流式版本，更推荐使用双向流式模式（优化版本），性能相对更优。

**问题答案：**
- **区别**：双向流式（`bigmodel`）= 边发边出字、低延迟；单向/流式输入（`bigmodel_nostream`）= 等音频 >15s 或末包才返回，准确率更高。**"按住说话边说边出字"必须用双向流式。**
- **推荐包长**：官方明确 **双向流式用 200ms 最优**（通用建议 100–200ms，间隔也是 100–200ms）。
- **是否有 `end_window_size` 这类 VAD 参数、默认多少（决定松手后多久出最终结果）**：**有**。官方原文：

| 参数 | 官方原文 |
| --- | --- |
| `end_window_size` | 强制判停时间。单位ms，**默认为800，最小200**。静音时长超过该值，会直接判停，输出definite。配置该值，不使用语义分句，根据静音时长来分句。用于实时性要求较高场景，可以提前获得definite句子 |
| `vad_segment_duration` | 语义切句的最大静音阈值。单位ms，**默认为3000**。当静音时间超过该值时，会将文本分为两个句子。不决定判停，所以不会修改definite出现的位置。**在end_window_size配置后，该参数失效** |
| `force_to_speech_time` | 强制语音时间。单位ms，最小1。音频时长超过该值之后，才会尝试判停并返回definite=true，需配合end_window_size参数使用……推荐设置1000，可能会影响识别准确率 |
| `enable_nonstream` | 开启二遍识别……开启二遍识别后，**会默认开启VAD分句（默认800ms判停，数值可通过end_window_size参数配置）**……且只有在非流式（nostream接口）输出的识别结果中会输出 `"definite": true` 分句标识 |

**给主人的大白话**：松手后多久能拿到"最终确定的一句话"，取决于 `end_window_size`——默认 **800ms 静音**才判停。想更"跟手"（松手就出字），把它调到 200–300；代价是断句更碎、可能把一口气的话切成两句，而且**一旦配了它就关闭语义分句**。
另外注意一个容易误解的点：**`show_utterances=true` 才会返回 utterances 分句信息**（含 `definite`），不开就只能拿到整段 `result.text`。

### C2. `finish-task` 的 payload；`task-finished` 是否一定会返回

官方原文（finish-task）：

> 说明：通知服务端音频发送完毕，请求结束任务。
> 发送时机：所有音频数据发送完毕后。
> 响应事件：服务端返回 `task-finished` 事件。
> header（必选）… action 固定为 `finish-task`。task_id 需与 run-task 事件中的 task_id 保持一致。streaming 固定为 `duplex`。

官方原文（交互流程第 4、5 步）：

> 4. 通知服务端结束任务：客户端发送 finish-task 指令通知服务端结束任务，**并继续接收服务端返回的 result-generated 事件**。
> 5. 任务结束：客户端收到服务端返回的 task-finished 事件，标志着任务结束。

**关键判断（重要）：**
- 官方明确说明了 finish-task 之后**还会继续来 `result-generated`**（末句最终结果），**然后**才是 `task-finished`。所以代码逻辑必须是"等到 task-finished 才算收尾"，不能一发出 finish-task 就立刻关连接——**否则会丢掉最后一句文本**。

> task-failed …… 连接会被关闭，无法复用。error_code: CLIENT_ERROR，error_message: "request timeout after 23 seconds."

  即**存在只回 task-failed、不回 task-finished 的路径**。
- 结论措辞：**官方承诺的"正常路径"是 finish-task → (若干 result-generated) → task-finished；官方未对"异常路径"做任何保证，异常时会走 task-failed 并断开。** 因此代码必须双监听，且加超时兜底。

### C3. `payload.output.sentence.text` 的语义；`sentence_begin` / `sentence_end` / `heartbeat` 含义

**结论：置信度：高（官方原文）。**

官方原文（result-generated）：

> 说明：识别结果，包含中间结果（**sentence_end=false**）和最终结果（**sentence_end=true**）。其中，**新句子的首个中间结果包含 sentence_begin=true**。

官方字段表原文：

| 属性 | 官方说明 |
| --- | --- |
| `text` | 识别文本 |
| `heartbeat` | 若为 true，可跳过该结果（心跳包） |
| `sentence_begin` | 用于标识句子开始 |
| `sentence_end` | 是否句子结束（true=最终结果，false=中间结果） |

| `begin_time` / `end_time` | 句子开始/结束时间（ms）。中间结果中 `end_time` 可能为 `null`，待句子结束（sentence_end=true）时填充最终值 |

- **置信度说明**：官方文档**没有**用一句"这是累计全量文本"来直白说明 `text`。但官方 SDK 文档给出了判定句结束的**实现依据**（很有说服力）：

> `is_sentence_end` …… 该方法通过检查 `sentence` 中 `end_time` 字段是否为 `None` 来判定——`end_time` 不为 `None` 时表示句子已结束。
> （https://help.aliyun.com/zh/model-studio/fun-asr-realtime-python-sdk ）

## D. Chromium / Electron / Windows 行为

### D1. Windows 上按住 Ctrl 时用 SendInput 注入 VK_BACK，目标程序收到的是"普通退格"还是"Ctrl+Backspace"？

**结论（分两层，必须分开说）：**
1. **SendInput 注入的按键本身不带修饰键状态位**——`INPUT`/`KEYBDINPUT` 结构里根本没有"Ctrl 是否按下"这个字段，输入流里只有 VK_BACK 的按下/抬起。**置信度：高（官方结构定义 + 官方原文）。**
2. **但目标程序是否会把它当成 Ctrl+Backspace，完全取决于目标程序怎么读修饰键状态**：如果它调 `GetKeyState` / `GetAsyncKeyState` / `GetKeyboardState`，会看到"Ctrl 当前是按下状态"（因为物理 Ctrl 真的按着），于是**就会当成 Ctrl+Backspace**；如果它只看 WM_CHAR 的字符码，则会看到被 Ctrl 影响后的字符码。**置信度：高（官方 API 语义），但"具体某程序的行为"属于实现相关，无法用官方文档一一担保。**

**官方原文依据：**

MSDN `SendInput`（https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput ）Remarks：

> This function does not reset the keyboard's current state. **Any keys that are already pressed when the function is called might interfere with the events that this function generates.** To avoid this problem, check the keyboard's state with the GetAsyncKeyState function and correct as necessary.

→ 这是**官方明确的警告**：调用 SendInput 时已经按下的键会干扰它生成的事件。**也就是官方承认"物理按住的 Ctrl 会影响注入按键的语义"**——这正是主人问题的官方依据。

MSDN `GetKeyState` Remarks：

> The key status returned from this function changes as a thread reads key messages from its message queue. The status does not reflect the interrupt-level state associated with the hardware. Use the GetAsyncKeyState function to retrieve that information.
> An application calls GetKeyState in response to a keyboard-input message. **This function retrieves the state of the key when the input message was generated.**

→ 官方明确：GetKeyState 返回的是"该输入消息生成时"的按键状态。

MSDN `GetAsyncKeyState`：

> Determines whether a key is up or down **at the time the function is called**… The most significant bit of the return value is set if the specified key is currently down.
> 官方示例里就是用它判断 Ctrl：`if (GetAsyncKeyState(VK_CONTROL) < 0) considerSafeMode = TRUE;`

→ 官方明确：这是"此刻"的物理键状态。

**Chromium/Electron 这一侧的具体行为（源码依据，置信度：中高）：**
Chromium 在 Windows 上把原生消息转成键盘事件时，**修饰键标志是从"全局按键状态"读的**，源码原文（`ui/events/win/events_win_utils.cc`）：

```cpp
// Returns a mask corresponding to the set of pressed modifier keys.
// Checks the current global state and the state sent by client mouse messages.
int KeyStateFlags(const MSG& native_event) {
  int flags = GetModifiersFromKeyState();
  ...
}
int GetModifiersFromKeyState() {
  int modifiers = EF_NONE;
  ...
    if (ui::win::IsCtrlPressed())
      modifiers |= EF_CONTROL_DOWN;
  ...
}
```

→ 因此 **Electron/Chrome 里被 SendInput 注入的 VK_BACK，会带着 `ctrlKey = true`**（因为物理 Ctrl 按着），在网页里就是一次真正的 **Ctrl+Backspace**。

**给主人的实践结论（重要）：**
- 想单纯"删一个字"而**不想**被当成 Ctrl+Backspace：**必须在注入前先"隐藏" Ctrl 状态**。Windows 没有"只对注入事件屏蔽修饰键"的官方开关，可行做法有三种（都属于工程手段，非官方 API）：
  1. 注入前 `SendInput` 一个 Ctrl key-up，注入 VK_BACK 后再 Ctrl key-down 把状态还回去（会短暂打断物理 Ctrl 状态，需谨慎）；
  2. 用 `AttachThreadInput` + `SetKeyboardState` 改**调用线程**的键盘状态表（只影响本线程消息队列的 GetKeyState 语义，跨进程不保证生效）；
  3. 干脆**不要用按键注入**，改用直接写入文本的方式（见 D3 结论里的建议）。
- 反过来，如果**就是要**触发 Ctrl+Backspace：按住物理 Ctrl 再注入 VK_BACK 即可，但这条链路上"到底删多少"取决于目标程序（见 D2）。

### D2. Chromium/Blink 中 textarea 的 Ctrl+Backspace 默认行为；对中文（CJK）是删一个汉字还是删一整段？

**结论：**

```cpp
}
```

→ Blink 用的是 **ICU 默认词边界规则（UAX #29）**。按该规则，**汉字（Han）不属于"字母类"词，规则不像英文那样把连续字母聚成一个词，所以每个汉字左右都是词边界**。因此 **Ctrl+Backspace 在纯中文文本里通常只吃掉一个汉字**，不会"删掉一整句/一整段"。
→ **注意这只对纯中文成立**：中文里夹的英文单词/数字（如 `语音ASR识别`）会按英文词边界整体删除；标点符号的归属由 ICU 规则决定，可能连带删除空格或标点。**这就是"为什么删得不整齐"的原因。**
→ 我**没有**用真实界面做验证（按红线要求不做 GUI 测试），所以这条标"中"置信度，若要 100% 确认，建议做一次 30 秒的手工对拍（在 textarea 里输入"你好世界"后按 Ctrl+Backspace 看剩几个字）。

### D3. 带 Ctrl 修饰键的 keypress/char 事件会不会把字符插入 textarea？Blink 的判断条件

**结论（诚实结论，必须分层）：**
- **官方文档层面：未找到**任何官方文档或源码注释，明确写"带 ctrlKey 的 keypress/char 事件在 Blink 里会被直接丢弃、不插入文本"。**如实标注：Blink 的 `KeyboardEventManager::DefaultKeyboardEventHandler` 里没有针对 ctrlKey 的"禁止插入"判断。**
- **但我找到了单侧的、可引用的源码证据**，说明 Chromium 在**别的层**做了过滤（见下），并且**Windows 平台本身就不会为 Ctrl+组合键生成普通字符消息**。

**证据 1（Blink 源码原文，置信度：高——说明"这里没有 ctrl 判断"）：**

`third_party/blink/renderer/core/input/keyboard_event_manager.cc` 的 `DefaultKeyboardEventHandler` 全文只有 tab / escape / enter / space 等分支，**没有任何 ctrlKey/altKey/metaKey 的"拒绝插入"分支**：

```cpp
void KeyboardEventManager::DefaultKeyboardEventHandler(
    KeyboardEvent* event, Node* possible_focused_node) {
  if (event->type() == event_type_names::kKeydown) {
    ...
    frame_->GetEditor().HandleKeyboardEvent(event);
    if (event->DefaultHandled())
      return;
    ...
  } else if (event->type() == event_type_names::kKeypress) {
    frame_->GetEditor().HandleKeyboardEvent(event);     // ← 插入路径在这里
    if (event->DefaultHandled())
      return;
    if (event->key() == keywords::kCapitalEnter) {
      DefaultEnterEventHandler(event);
    } else if (event->charCode() == ' ') {
      DefaultSpaceEventHandler(event, possible_focused_node);   // ← 只有空格这条做了 ctrl/alt/meta 过滤
    }
  }
}
```

注意它**确实**给空格单独加了过滤（说明 Blink 有能力、也是有意识地做这类判断）：

```cpp
void KeyboardEventManager::DefaultSpaceEventHandler(KeyboardEvent* event, Node* possible_focused_node) {
  DCHECK_EQ(event->type(), event_type_names::kKeypress);
  if (event->ctrlKey() || event->metaKey() || event->altKey())
    return;          // ← 带修饰键的空格不触发翻页
  ...
}
```

→ 也就是说：**空格有专门的修饰键过滤，字符插入没有**。（标为：源码事实，高置信度；但"所以带 Ctrl 的字符一定会被插入"**不能**由此推出，见证据 2、3。）

**证据 2（Chromium 源码原文，置信度：高——说明"文字框控件层确实会过滤控制字符"）：**

`ui/views/controls/textfield/textfield.cc` 原文：

```cpp
void Textfield::InsertChar(const ui::KeyEvent& event) {
  ...
  // Filter out all control characters, including tab and new line characters,
  // and all characters with Alt modifier (and Search on ChromeOS, Ctrl on
  // Linux). But allow characters with the AltGr modifier. On Windows AltGr is
  // represented by Alt+Ctrl or Right Alt, and on Linux it's a different flag
  // that we don't care about.
  const base::char16 ch = event.GetCharacter();
  const bool should_insert_char = ((ch >= 0x20 && ch < 0x7F) || ch > 0x9F) &&
                                  !ui::IsSystemKeyModifier(event.flags()) &&
                                  !IsControlKeyModifier(event.flags());
  if (GetTextInputType() == ui::TEXT_INPUT_TYPE_NONE || !should_insert_char)
    return;
  DoInsertChar(ch);
```

以及同文件里的辅助函数（**特别有信息量**）：

```cpp
bool IsControlKeyModifier(int flags) {
  // XKB layout doesn't natively generate printable characters from a
  // Control-modified key combination, but we cannot extend it to other platforms
  // as Control has different meanings and behaviors.
#if defined(OS_LINUX)
  return flags & ui::EF_CONTROL_DOWN;
#else
  return false;
#endif
}
```

→ 官方注释直白承认：**"Control 修饰的按键组合在 Linux（XKB）上本来就不会产生可打印字符"**，而**其他平台（含 Windows）不能照搬这个假设**。
→ 并且它明确**过滤掉所有控制字符**（`ch < 0x20` 或 `0x7F` 区间）以及**所有带 Alt 修饰的字符**。这意味着：即便有控制字符漏到 UI 层，也会在 `Textfield::InsertChar` 被挡掉。
（注意：这是 **Views UI** 路径，即浏览器自己的输入框/地址栏；网页渲染进程里的 textarea 走的是 Blink 另一条路径，不能直接等同。）

**证据 3（Chromium 源码原文，置信度：高——说明"Ctrl 状态会被如实带进事件"）：**

`ui/events/win/events_win_utils.cc`：

```cpp
KeyEvent KeyEventFromMSG(const MSG& msg) {
  ...
  if (IsCharFromMSG(msg)) {                      // WM_CHAR / WM_SYSCHAR
    flags = PlatformKeyMap::ReplaceControlAndAltWithAltGr(flags);
    return KeyEvent(msg.wParam, key_code, code, flags, time_stamp);   // is_char = true
  } else { ... }
}
// 而 flags 来自 GetModifiersFromKeyState()，其中包含：
//   if (ui::win::IsCtrlPressed()) modifiers |= EF_CONTROL_DOWN;
```

→ 字符事件（`is_char = true`）**会带上当时真实的 Ctrl 状态**（除非该键盘布局把 Ctrl+Alt 视为 AltGr）。所以"带 ctrlKey 的 keypress"在 Chromium 里**是可能存在的**。

**证据 4（微软官方文档，置信度：高——说明"Ctrl+组合键产生的是控制字符，不是普通字符"）：**

MSDN Learn Win32 – Keyboard Input（https://learn.microsoft.com/en-us/windows/win32/learnwin32/keyboard-input ）官方原文：

> Some CTRL key combinations are translated into ASCII control characters. For example, CTRL+A is translated to the ASCII ctrl-A (SOH) character (ASCII value 0x01). **For text input, you should generally filter out the control characters.**

MSDN WM_CHAR：

> The WM_CHAR message contains the character code of the key that was pressed.

MSDN Using Keyboard Input 还给出官方示例，在 `WM_CHAR` 里对 `0x08`(退格)、`0x0A`、`0x1B` 等**明确"generate a beep, but are not otherwise processed"**（不当作可显示文本处理）。

→ 官方立场很清楚：**Ctrl+字母产生的是 ASCII 控制字符（0x01–0x1A），做文本输入时应当过滤掉；它们不是"可插入的字符"。**

**综合判断（给主人的可落地结论，置信度：中高）：**
- 在 **Windows + Chromium/Electron** 环境下，Ctrl 组合键**本来就不会生成"普通可打印字符"**；即使强行把 `WM_CHAR 0x7F`（DEL）喂给渲染进程，**Windows 应用与本仓库相关路径都有控制字符过滤**，实际能插进去的可能性很低。
- 但**"Blink 在 `DefaultKeyboardEventHandler` 里判断 ctrl/alt/meta 并拒绝插入"这个具体说法，我**没有**找到官方依据。`DefaultKeyboardEventHandler` 里对修饰键的判断**只出现在空格那条分支**（`DefaultSpaceEventHandler`）。
- **因此强烈建议主人不要依赖"注入 Ctrl+字符"来输入文本**。理由：这条链路跨了 OS 消息生成 → Chromium 事件转换 → Blink 事件分发 → 编辑器插入，中间任一层的过滤规则都是**实现细节**，官方从未承诺其行为，升级即可能变。
- **更稳的替代方案**（都属于 Electron/Chromium 的公开 API，不依赖控制字符）：
  1. `webContents.insertText(text)`（Electron 官方 API，直接插入文本，不经过按键语义）；
  2. Chrome DevTools Protocol 的 `Input.insertText`；
  3. 直接把识别结果写进页面的 `<textarea>` 的 value（配合 input 事件派发）；
  4. Windows 侧用 `SendInput` + `KEYEVENTF_UNICODE` 发送 Unicode 字符（官方文档支持的注入字符方式，不受键盘布局与 Ctrl 状态影响）。
  **我建议第 1 或第 2 条**，因为它们是"插入文本"语义，天然没有 Ctrl/控制字符这些坑。

### D4. `ScriptProcessorNode` 的 `onaudioprocess` 跑在主线程还是音频线程？为什么被废弃？

**结论：跑在**主线程（main UI thread）**。置信度：高（Chrome 官方博客原文直接证实）。**

官方依据：Chrome for Developers 官方博客《Audio Worklet is now available by default》（作者 Hongchan Choi，Chrome WebAudio 团队）
https://developer.chrome.com/blog/audio-worklet 原文（Background: ScriptProcessorNode 一节）：

> Audio processing in Web Audio API runs in a separate thread from the main UI thread, so it runs smoothly. To enable custom audio processing in JavaScript, the Web Audio API proposed a ScriptProcessorNode which **used event handlers to invoke user script in the main UI thread**.
> There are two problems in this design: **the event handling is asynchronous by design, and the code execution happens on the main thread.** The former induces the latency, and the latter pressures the main thread that is commonly crowded with various UI and DOM-related tasks causing either UI to "jank" or audio to "glitch". **Because of this fundamental design flaw, `ScriptProcessorNode` is deprecated from the specification and replaced with AudioWorklet.**

**→ 三个问题一次性都有官方答案：**
1. **在主线程**（"invoke user script in the main UI thread"）。
2. **废弃原因**：① 事件回调天生异步 → 引入延迟；② 代码跑在主线程 → 主线程忙（DOM/UI 任务）时会造成**界面卡顿（jank）或音频爆音（glitch）**。官方定性为 "fundamental design flaw"（根本性设计缺陷），并说明它**已从规范中废弃**，由 AudioWorklet 取代。

**给主人的大白话**：`createScriptProcessor` 就像"让前台小姐姐一边接待客人一边炒菜"——前台一忙，菜就糊（爆音），出菜也慢（延迟）。AudioWorklet 是"专门请了个后厨"。

### D5. AudioWorklet 的 `process()` 运行在哪个线程？

**结论：运行在音频渲染线程（audio rendering thread），全局作用域叫 `AudioWorkletGlobalScope`。置信度：高（同一篇 Chrome 官方博客原文）。**

官方原文：

> Audio Worklet keeps the user-supplied JavaScript code all within the audio processing thread. That means it doesn't have to jump over to the main thread to process audio. This means the user-supplied script code gets to **run on the audio rendering thread (`AudioWorkletGlobalScope`) along with other built-in `AudioNodes`, which ensures zero additional latency and synchronous rendering.**

补充官方原文（生命周期与线程间通信）：

> Additionally, the return value of the `process()` method can be used to control the lifetime of `AudioWorkletNode`……Returning `false` from `process()` method marks the processor inactive, and the WebAudio engine no longer invokes the method.
> `AudioWorkletNode` and `AudioWorkletProcessor` are equipped with a `MessagePort` for bi-directional communication.

→ **实操要点**：`process()` 里**绝对不能**碰 DOM、不能用 `setTimeout`、不能做重活（如 JSON 解析大对象、写 localStorage）。要给主线程送数据，用 `this.port.postMessage()`（结构化克隆，有开销，建议传 `Float32Array` 的 `transferable` 或降采样后的定长数据）。

### D6. Electron 里 `new AudioContext()` 无用户手势会不会被挂起？`webPreferences.autoplayPolicy` 默认值？

**结论：Electron 官方文档明确 `autoplayPolicy` 默认为 `no-user-gesture-required`（即不需要用户手势）。置信度：高（Electron 官方文档原文）。但"由此推出 AudioContext 一定不会被 suspended"属于合理推断，不是官方承诺（标为高置信度推断）。**

官方原文（Electron 官方文档 WebPreferences）
https://www.electronjs.org/docs/latest/api/structures/web-preferences ：

> `autoplayPolicy` string (optional) - Autoplay policy to apply to content in the window, can be `no-user-gesture-required`, `user-gesture-required`, `document-user-activation-required`. **Defaults to `no-user-gesture-required`.**

**给主人讲清楚这三档的意思：**
| 取值 | 人话 |
| --- | --- |
| `no-user-gesture-required`（默认） | 页面可以随便出声、随便建音频上下文，不需要用户先点一下 |
| `user-gesture-required` | 必须用户先点过页面（手势）才能出声 |
| `document-user-activation-required` | 更严：必须有"文档级激活"（用户真实交互过）|

**关于 `new AudioContext()` 会不会被挂起为 `suspended`：**
- MDN 的 `AudioContext()` 构造函数页（https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/AudioContext ）**只讲了参数（latencyHint / sampleRate / sinkId）、返回值、异常，没有讲自动播放策略下的挂起行为**——我在这里没有找到官方原文，如实标注。
- 基于 Electron 的官方默认值 `no-user-gesture-required`，**在 Electron 里用全局快捷键（非页面手势）创建 AudioContext，不应被自动播放策略挂起**。这是**推断**（Confidence: 高，但不是文档原话）。
- **工程上的稳妥做法（与官方无冲突）**：任何情况下都加一个兜底——
  ```js
  if (ctx.state === 'suspended') { await ctx.resume(); }
  ```
  并在 `ctx.onstatechange` 里记录状态变化。这样即使宿主把 `autoplayPolicy` 配成了 `user-gesture-required`，也能第一时间发现并按需降级（例如提示用户在窗口里点一下）。
- 顺带一个官方限制（MDN 原文）："Prior to version 66 Google Chrome only supported up to six audio contexts per tab at a time."——**别每次录音都 new 一个 AudioContext**，复用同一个。

### D7. `getUserMedia` 首次调用延迟量级；反复开关麦克风 vs 常开 stream 的代价

**结论：官方文档没有给出量化的延迟数字（如实标注）。有两次大规模实测数据（社区，非官方）可参考。**

**（1）有没有官方量化数据？→ 未找到官方依据。**
MDN `getUserMedia` 页面只写了权限与错误语义，没有任何耗时指标。唯一能算"官方相关"的量化说法来自 MDN：
> In certain cases, it may be necessary to release the current camera facing mode before you can switch to a different one. To ensure the camera switch, it is advisable to free up the media resources by invoking the `"stop()"` method on the track before requesting a different facing mode.

→ 官方 MDN 反而**建议**在需要切换/释放时**主动 stop()**，说明"停掉再开"是官方认可的正常用法（代价它没量化）。

**（2）社区大规模实测（明确标为社区依据，非官方）：**

- **Philipp Hancke（WebRTC 领域知名开发者）基于生产数据的统计**（2016，Medium）
  https://medium.com/@fippo/getusermedia-prompts-ea912fba9e5d 原文：
  > In Chrome, **about 45% of the calls succeed within less than 100ms, more than 75% in less than 500ms**. This is too fast for most humans to react so it is safe to assume that the permission to the devices is persisted.
  → 即**已授权后的 Chrome，大头在百毫秒级**（45% <100ms，75% <500ms）。
  → 另外他也说明 Firefox 因为每次弹权限框，平均要**约 3 秒**（这属于"权限 UI 耗时"，不是硬件耗时）。

- **addpipe 基于约 10 万次真实 `getUserMedia()` 调用的统计**（2019）
  https://blog.addpipe.com/getusermedia-camera-microphone-initialization-times/ 原文：
  > instantly responding cameras & microphones are just a myth, the time hardware takes to initialize differs and it varies quite a bit BUT
  > **80% of times the hardware initializes in under 1 second; 95% of times in under 2 seconds.**
  → **硬件初始化本身**：80% <1s，95% <2s。

- **Chromium 官方邮件组讨论（`media-dev`）**：有开发者报告 Windows 上 `getUserMedia()` 极端情况下长达 **16 秒**；Chrome 团队的回复与后续结论指向"摄像头/麦克风驱动、杀软干扰、页面失焦导致 promise 被延迟 resolve"等原因，最终用户自查后确认是**本机环境问题**（JS 负载高 / 驱动 / 安全软件），**不是浏览器内部 bug**。
  https://groups.google.com/a/chromium.org/g/media-dev/c/LbfK6hZTF-A
  → 关键官方侧说法（来自该线程）：**页面失焦时，promise 可能不会被立即 resolve**（"it's more likely that the page was somehow out of focus and the GetUserMedia was prevented from being resolved immediately due to privacy policy"）。

**（3）"反复开关"vs"保持常开"的代价对比 —— 结论（工程判断，明确标注为推断，无直接官方结论）：**

| 维度 | 反复开关（每次 stop track + 重新 getUserMedia） | 保持 stream 常开 |
| --- | --- | --- |
| 延迟 | 每次都要重走设备初始化，按上面数据**几十 ms ~ 数百 ms**，极端（驱动/杀软）可到秒级 | 0（立即可用），只需在开始/停止时启停 AudioWorklet 节点 |
| 权限/焦点风险 | 每次都可能触发权限或"页面失焦延迟 resolve" | 只在开头一次 |
| 麦克风指示灯 | 只在录音时亮，用户观感更"安心" | **一直亮**，用户可能以为被偷听 |
| 功耗/占用 | 低（不录音时设备可被释放/其他程序占用） | 持续占用采集设备（可能与其他软件抢占，也可能让系统无法进入低功耗） |
| 兼容性坑 | Windows 上有"设备被其他程序独占/驱动切换导致失败或长延迟"的报告 | 无 |

**给主人的建议（判断）**：如果是「按住说话」这种高频交互，**首选用"常开 stream + 按需启停处理节点"**，同时：
- 在 UI 上明确显示"麦克风已就绪/正在听"，缓解指示灯常亮的疑虑；
- 加"空闲 N 分钟后自动 stop track，下次按键前预热 getUserMedia"的折中策略（预热 = 提前 500ms 调 getUserMedia，把初始化时间藏到用户还没说完第一个字的窗口里）。
**注意**：把"常开 vs 开关"的代价拍成具体毫秒数，**没有官方数据**，只能靠本地实测（建议主人自己跑一次 200 次的计时脚本，用 `performance.now()` 包住 getUserMedia，取下 P50/P95）。

> Qwen-Audio-3.0-ASR-Flash-Streaming/Fun-ASR-Realtime 的 WebSocket 连接支持复用：一个识别任务结束后，无需重新建立连接即可开启下一个任务。复用流程：客户端发送 `finish-task`，服务端返回 `task-finished` 后，可重新发送 `run-task` 开启新任务。

## F. 千问实时识别的收尾语义

### F1. 官方是否说明 `finish-task` 之后**一定**会回 `task-finished`？

**结论：官方**没有**使用"一定/保证"的措辞；官方只定义了"正常路径"的事件顺序，并单独定义了失败路径 `task-failed`（连接被关闭、无法复用）。置信度：高（对"官方未承诺"这一事实）。**

官方原文（客户端事件 · finish-task）：

> 说明：通知服务端音频发送完毕，请求结束任务。
> 发送时机：所有音频数据发送完毕后。
> 响应事件：服务端返回 `task-finished` 事件。

官方原文（WebSocket 接入指南 · 交互流程）：

> 4. 通知服务端结束任务：客户端发送 finish-task 指令通知服务端结束任务，**并继续接收服务端返回的 result-generated 事件**。
> 5. 任务结束：客户端收到服务端返回的 task-finished 事件，标志着任务结束。
> 6. 关闭连接：客户端关闭 WebSocket 连接。

官方原文（服务端事件 · task-failed）：

> 说明：任务失败，**连接会被关闭，无法复用**。
> 错误样例：`"error_code": "CLIENT_ERROR"`，`"error_message": "request timeout after 23 seconds."`

**"有没有可能只回 result-generated 的最终结果而不回 task-finished？"**
- **按官方文档：不存在这种"合法"路径。** 官方定义的"任务正常结束"的标志就是 `task-finished`；如果没收到它，说明落在了异常路径（`task-failed`、连接被断、或超时）。
- **但工程上必须当作"可能发生"来处理**：因为官方没有承诺"一定"，而且明确存在 `task-failed` + 断连的情况（官方样例给的就是 `request timeout after 23 seconds.`）。
- **落地建议（判断）**：发出 `finish-task` 后启动一个**收尾超时**（例如 5 秒）：
  - 期间继续接收并把 `result-generated`（含 `sentence_end=true`）落盘；
  - 收到 `task-finished` → 正常收尾；
  - 收到 `task-failed` → 记录 `error_code`/`error_message` 并按失败处理；
  - 超时未收到 `task-finished` → **把已经收到的最后一句 `sentence_end=true` 的结果当作最终结果使用**（因为这个结果本身是官方定义的"最终结果"），同时上报一条告警。
  **注意顺序：finish-task 之后还会来 result-generated（很可能就是最后一句的最终结果）。千万别在发完 finish-task 就立刻关连接，否则会丢最后一句。这一点官方原文写得很清楚。**

### F2. `payload.output.sentence.text` 是「当前分句累计」还是「整段累计」？

**结论：是「当前分句（sentence）内部的累计文本」，不是整段全局累计。置信度：高。**

理由（官方原文，三条独立证据）：
1. **有 `sentence_id` 分句标识**（官方服务端事件页原文）：
   > `sentence_id` integer 句子的序号标识。**正常识别结果中，sentence_id 从 1 开始递增。** 当 heartbeat 为 true 时（即心跳包），sentence_id 固定为 0。
   → 每条结果都带"第几句"，说明 `text` 是**该句范围**内的文本，而非从音频开头累计。
2. **官方对中间/最终结果的表述就是"当前句子"**：
   > 说明：识别结果，包含**中间结果（sentence_end=false）**和**最终结果（sentence_end=true）**。其中，**新句子的首个中间结果包含 sentence_begin=true**。
   > `usage`：当 `payload.output.sentence.sentence_end` 为 `false`（**当前句子未结束**）时，`usage` 为 `null`。当……为 `true`（**当前句子已结束**）时，`usage.duration` 为**当前任务**计费时长。
   → 官方用词是"当前句子"。
3. **时间戳的官方定义只在一句之内**：
   > 句级：`payload.output.sentence.begin_time` 与 `payload.output.sentence.end_time`，**标识整句在音频中的起止时刻**。中间结果中 `end_time` 可能为 `null`，待句子结束（`sentence_end = true`）时填充最终值。
   → `begin_time/end_time` 是"整句"的起止，不是"整段音频"的起止。

**（关于"句内是否需要覆盖而非追加"）**：官方 SDK 文档给了实现依据：
> `is_sentence_end` …… 该方法通过检查 `sentence` 中 `end_time` 字段是否为 `None` 来判定——`end_time` 不为 `None` 时表示句子已结束。
（https://help.aliyun.com/zh/model-studio/fun-asr-realtime-python-sdk ）

→ 同一句在"中间结果→最终结果"过程中是**同一对象在逐步补全**，所以官方 Python SDK 示例的打印方式就是每次直接 `print(sentence['text'])`（**不追加**）。
→ **实操结论**：用 `sentence_id` 做 key 缓存，同一 `sentence_id` 的 `text` **覆盖**；`sentence_end=true` 时**追加到最终文本**并清除该句缓存；`heartbeat=true`（`sentence_id=0`）**直接丢弃**。

> 说明一处官方措辞的不精确：官方 SDK 文档把 `is_sentence_end` 描述为"通过检查 end_time 是否为 None 判定"，而服务端事件文档里 `sentence_end` 是独立布尔字段。两者结论通常一致（句子结束时 `end_time` 也被填上），但**实现时以 `sentence_end` 布尔字段为准更稳**。标为：官方文档内部细微不一致。

### F3. 是否有 `heartbeat` 参数用于长静音保活？官方是否要求客户端定期发静音包？

**结论：有。官方在 run-task 的 `parameters` 里提供 `heartbeat` 布尔参数，默认 `false`。它只在"你持续发送静音音频"的前提下起保活作用——即官方**没有**说服务端会自己发心跳，而是**要求客户端（在开关打开时）持续发静音音频**，由服务端在该静音流上回心跳包。置信度：高（官方原文）。**

官方原文（客户端事件 · run-task · parameters）：

> `heartbeat` `boolean`（可选）是否启用心跳包。**默认值：false。**
> `true`：**在持续发送静音音频的情况下，可保持与服务端的连接不中断。**
> `false`（默认）：即使持续发送静音音频，连接也将在一定时间后因超时而断开。
> 静音音频指的是在音频文件或数据流中没有声音信号的内容。静音音频可以通过多种方法生成，例如使用音频编辑软件如 Audacity或 Adobe Audition，或者通过命令行工具如 FFmpeg。

官方对应服务端侧的字段（服务端事件 · result-generated）：

> `heartbeat` boolean **若为 true，可跳过该结果（心跳包）**。
> `sentence_id`：……当 heartbeat 为 true 时（即心跳包），**sentence_id 固定为 0**。

**三问的直接答案：**
1. **有 `heartbeat` 参数**（在 run-task 的 `parameters` 里，布尔，默认 `false`）。
2. **官方是否要求客户端定期发静音包？** —— **在开启 `heartbeat=true` 的前提下，是**：官方表述的前置条件就是"在**持续发送静音音频**的情况下"才保活。**官方没有说"开了 heartbeat 客户端就可以不发音频了"。** 所以"保持长连接"的责任在客户端：要么持续推静音 PCM，要么接受超时断连。
3. **超时具体多久？** —— 官方客户端事件页**没有给出具体超时秒数**。**如实标注：未找到官方依据（超时时长）。** 仅在 `task-failed` 的官方样例里出现过一个相关数字："request timeout after 23 seconds."（这看起来是**握手/首包阶段**的超时，不能直接等同于静音超时）。

**落地建议（判断）**：
- 方案 A（推荐）：开启 `heartbeat=true`，并在按下说话期间由音频节点持续输出（真实音频 + 无音频时补静音帧），天然满足"持续发送静音音频"。
- 方案 B（更省）：不开 heartbeat，在松手后主动发 `finish-task` 收尾；下次说话重新建连（官方支持连接复用：`finish-task` → `task-finished` 后可再发 `run-task`）。
- 无论哪种：**必须显式跳过 `heartbeat=true` 的结果帧**（`sentence_id=0`、`text` 通常为空），否则会把空文本覆盖到 UI 上。

## H. 无法证实的问题（如实列出）

1. **【D3 核心】** Blink 里"带 Ctrl 修饰键的 keypress/char 事件不会把字符插入 textarea" —— **未找到官方依据**。`KeyboardEventManager::DefaultKeyboardEventHandler` 中没有 ctrlKey/altKey/metaKey 的插入过滤分支（源码事实），但也没有任何官方文档/注释确认"因此不插入"。**结论只能是"跨层推断"，不能写成"官方规定"**。
2. **【D1 细节】** "Ctrl+Backspace 在 Windows 上必须产生 `WM_CHAR` = `0x7F`(DEL)" —— **未找到官方依据**。微软文档只说了"某些 CTRL 组合会被翻译成 ASCII 控制字符（例如 CTRL+A → 0x01）"，**没有点名 Ctrl+Backspace → 0x7F**。
3. **【B2 争议点】** 客户端末包到底"应该"用 `0b0010` 还是 `0b0011` —— **官方文档只给了 `0b0010` 的示例 + `0b0011` 的字段定义，没有给出"二者都可接受"或"必须用哪个"的明确表述**。两种写法都有真实代码在用，属于**协议可实现但未明确规范**的空档。**建议以官方示例 `0b0010` 为准**，但我不宣称 `0b0011` 一定失败。
4. **【B1 细节】** 新版控制台是否**完全废弃** `X-Api-App-Key`/`X-Api-Access-Key`（例如两套同时传会不会报错）—— 官方只写了"新版控制台只需要X-Api-Key即可"，**没有说明混传或旧值是否被拒绝**。
5. **【A3】** `16k_zh_en_2.0` 能否在 **48982（V2 老接口 /asr/v2/）** 上使用 —— 官方把 `16k_zh_en_2.0` 只写在 **V2 接口文档（131127）** 的引擎表里，**没有说明跨接口兼容性**。**未找到官方依据，不建议混用。**
6. **【A2】** 官方同一页里"包间隔超过 6 秒"与错误码"4008 超过 15 秒未发送"两个数字的确切关系（哪个先触发）—— **未找到官方澄清**。
7. **【C2/F1】** `finish-task` 之后 **是否保证**返回 `task-finished` —— **官方没有任何"一定/保证"措辞**；只定义了正常顺序，并给出 `task-failed` 的失败路径（且伴随断连）。**"会不会只回 result-generated 不回 task-finished"官方未表态**（按官方定义那属于异常路径）。
8. **【C3/F2】** `sentence.text` 用"累计全量文本"这个词来描述 —— **官方从未使用"累计/全量/增量"这类字样**。本报告的"句内累计"结论来自 `sentence_id` + `begin_time/end_time` 字段定义 + 官方 SDK 的 `is_sentence_end`（只看 `end_time` 是否 None）三处互证，属于**结构推断**，不是官方原话。
9. **【F3】** 静音导致的服务端超时**具体秒数** —— 官方客户端事件页**未给出**。只在 `task-failed` 样例里出现 `request timeout after 23 seconds.`（语境不同，不能等同）。
10. **【D6】** `new AudioContext()` 在无用户手势时是否被自动播放策略挂起为 `suspended` —— **MDN 的 AudioContext 页面没有讲这块**，Electron 文档只给了 `autoplayPolicy` 默认值。**"Electron 默认不会被挂起"是推断，不是官方声明。**
11. **【D7】** `getUserMedia` 首次调用的官方耗时指标 —— **官方文档没有任何量化数据**（只有社区实测）。"反复开关 vs 常开"的代价对比也**无官方结论**。
12. **【E2】** 通过 **DashScope 模型列表接口**实测确认 `qwen-audio-3.0-asr-flash-streaming` —— **未执行**（需要主人的 API Key，本会话未获授权调用）。结论仅基于官方文档三处交叉证实。
13. **可访问性限制（技术原因，非结论问题）**：
    - 火山 6561/1354869 页面在渲染时把接口地址域名换行截断（`wss://` + 换行 + `openspeech.bytedance.com/...`），我已用同站 SDK 文档（LargeModelStreamRecognitionSDK）交叉证实域名与路径，但**页面原文的完整 URL 字符串无法逐字引用**。
    - 阿里云 `paraformer-real-time-speech-recognition-websocket-api` 这个 URL 返回 **404**（我实测抓到的是阿里云 404 页），Paraformer 的实时 WebSocket 细节只能从 `asr-model` / 用户指南 / Python SDK 页面间接取证。
    - 内部 `ws_mcp_list` 只暴露了 Exa 一个 MCP 服务器（无 DashScope/内容侧工具），因此无法直接查 DashScope 在线模型列表。
