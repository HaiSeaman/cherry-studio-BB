## 二、结论摘要

代码库整体工程水准在同类桌面应用里属中上：3930 个测试全绿、三套 tsconfig 零类型错误、Zip Slip / 路径穿越 / 命令查找注入等常见坑**都有正确防护**、日志有轮转上限、构建期有硬失败校验（`copyKoffiNativeBinding`、`verify-asar-integrity`）。

但审计发现了 **4 个 Critical、21 个 High** 级问题，集中在三条主线上：

**主线一：渲染进程的信任边界被系统性放弃。** 主窗口 `webSecurity:false` + `allowRunningInsecureContent:true` + `webviewTag:true` 且全仓无 `will-attach-webview` 校验；CSP 写成 `script-src 'self' 'unsafe-eval' 'unsafe-inline' *`（等于没有）；preload 把原始 `ipcRenderer.invoke/send` 整体透传（无 channel 白名单）；200+ 个 `ipcMain.handle` **无一校验 sender**。而主窗口渲染的正是 LLM 输出、网页搜索结果、MCP 工具返回值这些不可信内容。这几条单独看都还能辩解，叠在一起就是一条完整的"一次 XSS → 完全控制用户机器"的通路。

**主线二：本分支新增的「自动化 / 桌面助手」功能是全仓最危险的一块代码。** `AutomationService.sysFileRead/Write/List` 对渲染进程传来的路径**零校验**（无白名单、无 realpath、无确认），`sysFileWrite` 还会自动 `mkdir -p` 任意父目录；`sysPower` 可无确认关机/重启。同分支引入的定时任务库用非原子写 + 解析失败即清空，崩溃时静默丢弃全部任务。这一块不是上游 Cherry Studio 的设计，是本 fork 自己加的，也是**修复性价比最高**的一块。

**主线三：中文场景下的功能正确性缺陷 + 供应链校验缺失。** `toCamelCase` 会把所有非 ASCII 字符删光，导致**所有中文命名的 MCP 服务器/工具全部塌缩成同一个函数名 `mcp__`**，工具互相覆盖、模型无法区分（已用 node 实测复现）。`resources/scripts/download.js` 在 1.3.3 提交中被删除，导致 uv/bun 自动安装 **100% 失败**。rtk 原生二进制从 GitHub release 下载后**无任何 checksum 校验**，却在运行期被用来改写即将执行的 shell 命令。CherryAI 的 HMAC 签名密钥后缀硬编码在源码里，且构建期把 `global.CHERRYAI_CLIENT_SECRET` 内联成 `void 0`，出厂产物的签名密钥就是公开可算的字符串 `undefined.GvI6I5Zr…`。

**性能方面**，最值得动手的是三处流式渲染热点（Markdown `components` 每帧重建导致 Shiki 高亮子树整棵 remount、`streamingTextProjection` 每个 chunk 全文重扫 O(n²)、每次块转换全量重估历史 token 并重复走 IPC 读文件）以及 redux-persist 的**无节流全量序列化写放大**（拖一个透明度滑块 = 每秒数十次数 MB JSON.stringify + 跨窗口广播）。

## 三、Critical 级问题（4 项，建议立即处理）

### C1. Automation IPC 提供无限制的任意文件读写与关机能力，且无 sender 校验

**位置**：`src/main/services/AutomationService.ts:372-415`（sysFileRead / sysFileWrite / sysFileList）、`:417-437`（sysPower）；注册于 `src/main/ipc.ts:421-431, 434-435`；preload 暴露于 `src/preload/index.ts:532-539`；渲染端调用 `src/renderer/src/automation/systemTools.ts:84-93`

**现象**（已亲自 Read 验证）：

```ts
// AutomationService.ts:393-401
public async sysFileWrite(filePath: string, content: string): Promise<AutomationSysFileResult> {
  try {
    await fsp.mkdir(path.dirname(filePath), { recursive: true })   // 自动创建任意父目录
    await fsp.writeFile(filePath, content, 'utf8')                 // 任意绝对路径，零校验
    return { ok: true, content: `已写入 ${Buffer.byteLength(content, 'utf8')} 字节到 ${filePath}` }
  } catch (e) { ... }
}
```

三个接口都直接把渲染进程传来的字符串交给 `fsp`，**没有**白名单、没有 `resolveAndValidatePath`、没有 realpath 检查、没有用户确认。唯一存在的"授权"是渲染端 `systemTools.ts:22-24` 的一个 `granted` 数组——纯客户端状态，主进程完全不知情。

对比证据：同一个 `ipc.ts` 里的 `Open_Website` 有 `isSafeExternalUrl` 校验（`:124-130`），说明项目**已经掌握了正确的模式**，只是没有用在这几个通道上。

**攻击链**：主窗口渲染 LLM 输出、网页搜索结果、MCP 工具返回值（均不可信）。任一处 XSS 即可：
1. 写入 `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\evil.bat` → 下次登录持久 RCE；
2. 或 `Open_Path`（`ipc.ts:548-550`，裸 `shell.openPath(path)`）直接执行任意可执行文件；
3. 或覆写 app 数据目录下的 redux-persist 文件，注入一个 `command` 任意的 stdio MCP server；
4. 或读取 `~/.ssh/id_rsa`、浏览器 Cookie 库并外传（CSP `connect-src *` 不拦）；
5. `sysPower('shutdown')` → 无条件关机（数据丢失型 DoS），且可被定时任务无人值守触发。

**修复**：
- 主进程侧强制根目录白名单，复用已有的 `src/main/mcpServers/filesystem/types.ts:48-97` 的 `validatePath`（它对目标和根都做 realpath 再比较，能挡 `..`、绝对路径、符号链接逃逸）；
- 拒绝写入启动项目录、可执行扩展名、app 数据目录；
- `file_write` / `open_path` / `shutdown` 三类操作走**主进程级**确认对话框（不能只在渲染层确认）；
- `ipc.ts:434` 对 `sysPower` 的 action 做运行时枚举校验（当前传非法值会 `exec(undefined)` 抛 TypeError）；
- `shutdown /s` 是 Windows 专用命令，需加平台分支。

### C2. CherryAI 请求签名密钥公开化 + 无校验的签名预言机 IPC

**位置**：`src/main/integration/cherryai/index.js:10`、`src/main/config.ts:20`、`src/main/ipc.ts:836`

**现象**（已亲自 Read 验证）：

```js
// src/main/integration/cherryai/index.js:9-11
function getClientSecret() {
  return global.CHERRYAI_CLIENT_SECRET + '.GvI6I5ZrEHcGOWjO5AKhJKGmnwwGfM62XKpWqkjhvzRU2NZIinM77aTGIqhqys0g'
}
```

```ts
// src/main/config.ts:20
global.CHERRYAI_CLIENT_SECRET = import.meta.env.MAIN_VITE_CHERRYAI_CLIENT_SECRET
```

`.env` 与 `.env.example` 中**均未定义** `MAIN_VITE_CHERRYAI_CLIENT_SECRET`（我读了这两个文件，只有 `NODE_OPTIONS` 和 `CSLOGGER_*`）。`MAIN_VITE_*` 前缀的变量由 Vite **静态内联**进产物。子代理实测解析 `dist/win-unpacked/resources/app.asar` 确认：`out/main/index.js` 内是 `global.CHERRYAI_CLIENT_SECRET = void 0;`，且偏移 940271 处含完整字面量密钥后缀。

**结论**：出厂产物的 HMAC-SHA256 签名密钥就是公开可算的字符串 `"undefined.GvI6I5Zr…"`。`X-Client-ID / X-Timestamp / X-Signature` 三件套对任何人都可伪造，等于**对 CherryAI 后端完全没有认证**。即便将来注入真实 secret，`MAIN_VITE_` 前缀也必然把它内联进 bundle，仍可完整还原——这是设计层面的错误，不是配置疏漏。

雪上加霜：

```ts
// src/main/ipc.ts:836
ipcMain.handle(IpcChannel.Cherryai_GetSignature, (_, params) => generateSignature(params))
```

不校验 `params`（为 `undefined` 时解构还会抛错）、不校验 sender。任意渲染上下文可对任意 `method / path / query / body` 取得合法签名。

另注：`src/main/integration/cherryai/index.js` 同时被 `.oxlintrc.json` 的 `ignorePatterns`、`eslint.config.mjs` 的 `ignores`、`biome.jsonc` 的 `!src/main/integration/**` 三处显式排除，且是仓库里唯一的 `.js`（非 `.ts`）主进程源码——**恰好是这个藏着 Critical 密钥的文件完全脱离了静态检查**。

**修复**：
1. 改为运行期读取（`process.env` 不被 Vite 内联）或安全存储；正解是**服务端换发短期 token**，客户端永不持有长期签名密钥；
2. 已泄漏的密钥必须在服务端轮换（git 历史里也有）；
3. `Cherryai_GetSignature` 白名单化 host/path，校验 `event.senderFrame`，参数用 zod 校验；
4. 把该文件改回 `.ts` 并纳入 lint 覆盖。

### C3. MCP 工具名：所有中文名称塌缩成同一个 `mcp__`

**位置**：`packages/shared/mcp.ts:14-26`（`toCamelCase`）、`:110-116`（`buildFunctionCallToolName`）；调用方 `src/main/services/MCPService.ts:925`

**现象**（已用 node 实测复现）：

```ts
// mcp.ts:15-20
let result = str
  .trim()
  .toLowerCase()
  .replace(/[^a-z0-9]+(.)/g, (_, char) => char.toUpperCase())
  .replace(/[^a-zA-Z0-9]/g, '')   // ← 中文字符在这一步被全部删除
```

```
toCamelCase("工具")       → ""
toCamelCase("我的服务器") → ""
buildFunctionCallToolName("我的服务器", "工具")     → "mcp__"
buildFunctionCallToolName("另一个服务器", "别的工具") → "mcp__"
buildFunctionCallToolName(undefined, "获取天气")     → "mcp__"
```

**影响**：中文命名的 MCP 服务器与工具（本分支产品名为 Cherry-Studio-BB，面向中文用户，这是**极常见**场景）全部得到同一个函数名 `mcp__`，工具在 `tools` 映射里互相覆盖，模型无法区分调用哪个，且**无任何日志**。

**同一条链上的第二个缺陷**：`buildFunctionCallToolName` 只传了 `prefix/delimiter/maxLength`，**没有传 `existingNames`**。而 `buildMcpToolName` 的去重逻辑是：

```ts
if (!existingNames) {
  return maxLength ? truncateToLength(baseName, maxLength) : baseName   // 直接返回，跳过去重
}
```

子代理实测：两个仅在结尾 `range`/`limits` 不同的长工具名，截断到 63 字符后**完全相同**（`mcp__filesystem__readMultipleLargeTextFilesFromDirectoryWithEnc`）。调用 A 工具实际命中 B 工具，静默。

**修复**：
- `toCamelCase` 改用 Unicode 感知的 `\p{L}\p{N}`，保留非 ASCII；或对空结果回退到 `_<短哈希>`；
- `buildFunctionCallToolName` 增加 `existingNames` 参数，`MCPService.listToolsImpl` 维护 per-server `Set` 传入，碰撞时告警；
- 结果为空/重复时必须抛错而非静默返回；
- 补测试：`src/main/__tests__/mcp.test.ts` 有 40 个用例，但**全是 ASCII 名称**，中文塌缩与 63 字符碰撞均无覆盖。

### C4. 渲染进程 CSP 完全失效

**位置**：`src/renderer/index.html:8`；同样宽松策略见 `miniWindow.html:8`、`selectionAction.html:8`、`selectionToolbar.html:8`

**现象**（已亲自 Read 验证）：

```html
<meta http-equiv="Content-Security-Policy"
  content="default-src 'self'; connect-src blob: *; script-src 'self' 'unsafe-eval' 'unsafe-inline' *;
           worker-src 'self' blob:; style-src 'self' 'unsafe-inline' *; font-src 'self' data: *;
           img-src 'self' data: file: * blob:; media-src 'self' file: blob: http: https:; frame-src * file:" />
```

- `script-src` 含 `*` + `'unsafe-inline'` → CSP 对 XSS **零防护**；
- `connect-src *` → 允许向任意域外发数据，窃取后外传毫无阻碍；
- `frame-src * file:` → 允许加载任意远端与本地文件。

**反证**：同仓库的 `src/renderer/musicWidget.html:8` 用的是严格策略 `default-src 'self'; connect-src 'self' ws:; style-src 'self' 'unsafe-inline'; img-src 'self' data:`——说明本项目**完全有能力**收敛 CSP，只是主窗口没做。

关于 `'unsafe-eval'`：全仓 `src/ packages/ scripts/ resources/` grep `eval(` 与 `new Function(` **零命中**（第一方代码不用 eval），所以它是某个第三方依赖要求的（未定位到具体依赖，推测 mermaid/shiki 一类，**未验证**）。

**修复**：生产已 bundle，`'unsafe-inline'` 与 `*` 都不需要。`script-src 'self'`（若确需 eval 改 `'wasm-unsafe-eval'`）；`connect-src` 收敛到用户配置的 provider host + MCP host；`frame-src` 去掉 `*`。这一条是**成本最低、收益最大**的纵深防御补强，且不影响功能。

## 六、性能与资源占用专项

用户特别关心性能，这里单列并按"收益/成本比"排序。

### P1【最高优先】流式渲染三大热点

**P1-a：Markdown `components` 依赖全文内容 → 自定义组件每帧被 unmount/remount**
- 位置：`components/Markdown.tsx:149-169`（`useMemo(..., [block.id, messageContent])`，内含 `a/code/table/img/pre/p` 内联箭头函数）、`:134`（每次渲染对全文跑 `ALLOWED_ELEMENTS.test(messageContent)` O(n) 正则）
- 机理：流式时 `messageContent` 每 ~66ms 变化 → components 对象重建 → ReactMarkdown 产出的元素 `type`（函数身份）变化 → React 视为**不同组件类型**，整棵链接/代码块/表格子树卸载重建。Shiki 高亮的 CodeBlock 重建成本极高。
- 量级：长回复含多个代码块/链接时，约 15fps × 全子树 remount。这是流式阶段**最大的单点渲染开销**。
- 方案：`components` 只依赖 `block.id` 与一个布尔 `hasStyleTag`（把正则结果存 state）；内联组件提为模块级常量。

**P1-b：`createStreamingTextProjection` 每个 chunk 全文重扫，O(n²)**
- 位置：`aiCore/callbacks/textCallbacks.ts:63-78` → `streamingTextProjection.ts:62-125`
- 机理：每收到 TEXT_DELTA（**未节流**）对全量 `text` 逐行扫描 + 每行正则。
- 量级：含代码围栏的回复，5 万字符 / 数千 chunk ≈ **上亿字符级扫描 + 数万次正则**，纯 CPU 浪费在 150ms 节流之前。
- 方案：增量解析（跨 chunk 保留 fence 状态，只扫新增 delta），或把 projection 移入节流后的渲染路径。

**P1-c：每次块转换全量重估历史 token + 重复 IPC 读文件**
- 位置：`pages/home/Messages.tsx:261-268`、`services/TokenService.ts:22-26,29-50,168-196`
- 触发链：`messageThunk` 每次 `handleBlockTransition`/消息落库都 dispatch `updateTopicUpdatedAt`（`assistants.ts:164-173`）→ assistant 对象换新引用 → effect 重跑；且 `onFirstUpdate` 是 `Chat.tsx:150` 的**内联函数**，Chat 每次渲染都换引用，effect 跟着重跑。
- 机理：`estimateHistoryTokens` 对上下文内全部消息 join 后 `approximateTokenSize` 全量扫描，且对无 usage 的带文件消息每次 `window.api.file.read` **走 IPC 重读磁盘**。
- 量级：10 万字符上下文 × 一次 agent 回复几十个块转换 ≈ 数百万字符扫描 + 每转换若干次文件 IPC，全部落在流式期间的主线程。
- 方案：按 `messageId+updatedAt` 缓存每条消息 token 数；`Chat` 用 `useCallback` 固化 `onFirstUpdate`/`onComponentUpdate`；estimate 结果节流。

### P2 redux-persist 全量序列化写放大（估计是最高频的日常卡顿源）

- 位置：`store/index.ts:65-74`（已亲自验证：配置里只有 `key/storage/version/migrate/blacklist`，**没有 throttle**）+ redux-persist v6 默认行为
- 机理：任一持久化 slice 的每个 action 都触发**全部**持久化状态 `JSON.stringify` + `localStorage.setItem`。
- 三个实测放大器：
  1. 划词透明度滑块拖动 —— `useSelectionAssistant.setActionWindowOpacity` 每 mousemove dispatch，`selectionStore` 既持久化又在 syncList 里跨窗口广播；
  2. 音乐音量滑块 `setVolume` 同型；
  3. 每条消息落库都 `dispatch(updateTopicUpdatedAt)`（`DexieMessageDataSource.ts:104`）→ assistants 全 slice 重写。
- 量级：助手/话题/模型多时 blob 可达数 MB，拖滑块期间 = **每秒数十次全量序列化 + N 窗口 IPC 同步**。
- 方案：persist 写入节流（≥1s）；高频 UI 偏好改存 Dexie settings 表或延迟持久化；slider 用 `onChange` 维护本地态 + `onAfterChange` 才提交 store。

### P3 历史搜索全表加载 + 二次复杂度（可导致 OOM）

- 位置：`pages/history/components/SearchResults.tsx:198-233`
- 机理：`db.message_blocks.toArray()` 把**全库所有块**（含工具输出、大文本）读进内存再过滤；`topics.flatMap(messages)` 后对每个命中块做 `messages.find` 线性扫描 → **O(blocks × messages)**；`useLiveQuery(db.topics.toArray)` 在流式期间（topics 表每 150ms 节流写）反复全量重读。
- 量级：重度用户数百 MB 堆占用、搜索数秒冻结甚至 OOM。
- 方案：按 messageId 建 Map、`where('type')` 收敛块集、搜索移入 worker、LiveQuery 加防抖或仅取 id 列表。

### P4 Context/Provider 未 memo 导致全应用重渲染

- `context/ThemeProvider.tsx:123`：value 是内联对象 + 每次渲染新建的 `toggleTheme`/`setTheme`；配合 `hooks/useSettings.ts:27` 订阅整个 settings slice → 任何 settings 字段变更 → ThemeProvider 重渲染 → **全应用所有 useTheme 消费者**重渲染。
- `AntdProvider` 同型：每次渲染内联数百行 theme 对象无 useMemo → antd 主题重算。
- 方案：`useMemo` 包裹 value/theme 对象；settings 按字段订阅（`useAppSelector(s => s.settings.theme)` 而非整个 slice）。

### P5 memo 链被 `{...message, index}` 击穿

- `pages/home/Messages/filters.ts:92`（getGroupedMessages 每消息新建对象）→ `Messages.tsx:313-324` 每次 messages 变化重建全部组 → `memo(MessageGroup)`、`memo(MessageItem)`、`memo(MessageContent)`、`MessageBlockRenderer` 全部因新引用失效；`MessageGroup.tsx:160-181` 的 `onUpdateUseful` 也每次重建。
- `Messages.tsx:108-109` 注释宣称"消息对象引用稳定，React.memo 可跳过"，**与实际不符**。
- 附带：`MessageGroup.tsx:117-158` 两个 effect 依赖 `[messages]`，每次转换对组内每条消息做 EventEmitter off/on + `getElementById` DOM 遍历。
- 方案：index 用独立 prop 传而非 spread 进 message；`onUpdateUseful` 用 ref 稳定化；LOCATE_MESSAGE 监听改为按 id 委托。

### P6 无虚拟滚动

消息列表用 `react-infinite-scroll-component`（inverse）+ 分页（默认 10 组，每次 +20，`Messages.tsx:334-341`、`constant.ts:24`），未用 react-window/virtuoso。分页缓解了首屏，但用户翻完 1000+ 条后全部为真实 DOM，叠加 P5 每次转换全列表协调 + 布局成本。

## 附录：一句话总结

**这个 fork 的工程基础扎实（类型零错误、3930 测试全绿、多处安全防护做得比同类项目更好），但它在两个方向上同时失守：一是把渲染进程当成可信环境（CSP/webSecurity/sender 校验/路径白名单四道防线全部缺席，而它渲染的恰恰是 LLM 输出这种最不可信的内容），二是对中文场景与供应链完整性缺乏验证（中文 MCP 工具名全部塌缩、关键安装脚本被删、原生二进制无校验和下载）。** 前 8 项修复里有 5 项是"改几行配置/加一个 handler"级别的工作量，建议优先清掉。
