## 五、数据模型与核心协议(新增章节)

### 5.1 Workflow 持久化类型(`src/renderer/src/pages/workflows/types.ts`)

```ts
import type { Edge, Node } from '@xyflow/react'

/** 节点业务参数(按 type 区分,见 5.3 节点 Schema) */
export type WorkflowNodeType = 'start' | 'llm' | 'http' | 'text' | 'condition'

/** 节点运行状态(四态+剪枝态) */
export type NodeRunStatus = 'idle' | 'running' | 'success' | 'error' | 'skipped'

export interface WorkflowNodeData extends Record<string, unknown> {
  label: string
  type: WorkflowNodeType
  params: Record<string, unknown> // 各类型节点的业务参数,执行前经 zod 校验
}

export type WorkflowNode = Node<WorkflowNodeData>

/** condition 节点的 true/false 分支通过 sourceHandle 区分 */
export type WorkflowEdge = Edge

export interface NodeRunResult {
  nodeId: string
  status: NodeRunStatus
  output?: Record<string, unknown>
  error?: string
  durationMs: number
}

export interface WorkflowRunRecord {
  status: 'running' | 'success' | 'error' | 'stopped'
  startedAt: number
  finishedAt?: number
  results: Record<string, NodeRunResult> // nodeId → 结果
}

export interface Workflow {
  id: string // crypto.randomUUID()
  name: string
  description?: string
  nodes: WorkflowNode[]
  edges: WorkflowEdge[]
  createdAt: number
  updatedAt: number
  lastRun?: WorkflowRunRecord
}
```

> 说明:运行态(`running/success` 等)只存在组件 state,**不入库**;`lastRun` 仅在运行结束时写入一次。历史运行记录(多次)推迟到阶段 4 评估是否需要 `workflow_runs` 表。

### 5.2 AI 操作协议(zod schema,`engine/protocol.ts`)

```ts
import { z } from 'zod'

const NodeParamsSchema = z.record(z.string(), z.unknown())
const PositionSchema = z.object({ x: z.number(), y: z.number() }).optional()

const NodeSchema = z.object({
  id: z.string().min(1),
  type: z.enum(['start', 'llm', 'http', 'text', 'condition']),
  label: z.string(),
  params: NodeParamsSchema.default({}),
  position: PositionSchema // 可省略,布局引擎会重排
})

const EdgeSchema = z.object({
  source: z.string(),
  target: z.string(),
  sourceHandle: z.string().optional() // condition 节点: 'true' | 'false'
})

/** thinking 前置:业界验证过的准则——先推理后结论,可显著提升输出质量 */
export const CopilotActionSchema = z.object({
  thinking: z.string().optional(),
  action: z.enum(['generate', 'addNode', 'updateNode', 'deleteNode', 'layout', 'clear']),
  nodes: z.array(NodeSchema).optional(),
  edges: z.array(EdgeSchema).optional(),
  payload: z.unknown().optional()
})

export type CopilotAction = z.infer<typeof CopilotActionSchema>
```

协议要点:

1. **thinking 字段放在 JSON 最前**——模型先写出计划再给出结论,输出质量更高,同时该字段可直接展示给用户当"AI 的说明";
2. **schema 扁平化**——嵌套不超过 2 层,避免弱模型在深层结构上出错;
3. **position 可选**——AI 无需精确坐标,布局引擎统一重排,降低协议复杂度;
4. `updateNode` 的 `payload` 里用 `{ id, patch: { label?, params? } }` 结构,只改增量。

### 5.3 节点参数 Schema(先定 Schema 再写节点,顺序不能反)

| 节点          | 参数 Schema(params)                                                                                                                                                    | 输出 Schema(outputs)                                |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `start`     | `{ input: string }`(运行时由用户在输入框填写)                                                                                                                                    | `{ input: string }`                               |
| `llm`       | `{ modelId: string, systemPrompt: string, userPrompt: string }`(prompt 均支持模板)                                                                                        | `{ text: string }`                                |
| `http`      | `{ url: string, method: 'GET'\|'POST'\|'PUT'\|'DELETE', headers?: Record<string,string>, body?: string }`                                                            | `{ status: number, data: unknown }`               |
| `text`      | `{ template: string }`                                                                                                                                               | `{ text: string }`                                |
| `condition` | `{ conditions: Array<{ left: string, operator: '=' \| '≠' \| '>' \| '<' \| '≥' \| '≤' \| 'contains' \| 'notContains', right: string }>, combinator: 'and' \| 'or' }` | 无输出数据,仅路由:`{true}` / `{false}` 两个出边(sourceHandle) |

条件表达式 `left` / `right` 均为模板字符串(如 `{{llm_1.text}}` 与 `100`),运行时先做模板替换再比较;`contains` 用 `String(left).includes(right)` 语义。

> **终点语义**:节点系统不含显式 `end` 节点——**无出边的节点即终点节点**,其输出即整个工作流的运行结果(RunPanel 中所有终点节点的输出合集)。

```ts
import dagre from '@dagrejs/dagre'

const NODE_WIDTH = 220
const NODE_HEIGHT = 72

export function getLayoutedElements(nodes: WorkflowNode[], edges: WorkflowEdge[], direction: 'TB' | 'LR' = 'TB') {
  const g = new dagre.graphlib.Graph().setDefaultEdgeLabel(() => ({}))
  g.setGraph({ rankdir: direction, nodesep: 50, ranksep: 80 })
  nodes.forEach((n) => g.setNode(n.id, { width: n.measured?.width ?? NODE_WIDTH, height: n.measured?.height ?? NODE_HEIGHT }))
  edges.forEach((e) => g.setEdge(e.source, e.target))
  dagre.layout(g)
  const layouted = nodes.map((n) => {
    const pos = g.node(n.id)
    // ⚠️ dagre 返回中心坐标,ReactFlow 锚点在左上角,必须减半宽高
    return { ...n, position: { x: pos.x - (n.measured?.width ?? NODE_WIDTH) / 2, y: pos.y - (n.measured?.height ?? NODE_HEIGHT) / 2 } }
  })
  return { nodes: layouted, edges }
}
```

### 阶段 3:运行调试引擎 ★ 技术难点(3\~4 天)

**步骤 3.1 —— 调度器(scheduler.ts):**

```ts
/**
 * 返回拓扑序节点 id 数组;存在环时抛出 CycleError(含环上节点名,便于用户定位)。
 * Kahn 算法:入度表 + 队列;处理数 < 总数 ⇒ 有环。
 */
export function topoSort(nodes: WorkflowNode[], edges: WorkflowEdge[]): string[]

/**
 * 运行前校验(全部通过才允许启动):
 * 1. 恰有一个 start 节点;
 * 2. 无环(topoSort);
 * 3. 所有边引用的 source/target 存在;
 * 4. condition 节点至少连出一条分支边(true/false 任一);未连出的分支视为终止,不算错误。
 */
export function validateWorkflow(/* ... */): string[] // 错误信息数组
```

执行语义:

- **串行执行**,按拓扑序 `await` 逐节点(并发限流是后续优化);

- **分支剪枝**:condition 节点求值后,未命中分支的**整条下游链**标记 `skipped`;skipped 节点的下游若同时被命中分支供养则正常执行(汇合语义);

- **每节点超时**:LLM 节点 10 分钟、HTTP 节点 30 秒、其余 5 秒(`AbortController` + `setTimeout`,参照 `automation/runner.ts` L157-158 的超时模式);

- **停止**:RunPanel 的 ⏹ 按钮触发全局 `AbortController.abort()`,所有进行中请求中断,已完成节点保留结果;

- 节点失败 → 该节点标 `error` + 下游全部 `skipped`,**整个运行不中断其余独立分支**(比"一错全停"更符合工作流直觉,实现也更简单:下游剪枝复用同一机制)。

**步骤 3.2 —— 节点执行器(executors.ts):**

- `start`:从运行输入框取值,产出 `{input}`;

- `llm`:**完全参照** **`automation/runner.ts`** **L115-207 的链路**:

  1. `getStoreProviders().find((p) => p.id === model.provider)` 定位 provider,校验模型仍存在;
  2. `getRotatedApiKey(baseProvider)` 处理 key 轮换(两者均来自 `@renderer/services/ApiService` 与 `@renderer/hooks/useStore`);

## 十一、测试策略(新增章节)

项目已配好 vitest 分工程(`pnpm test:renderer` 跑 renderer project)。以下三个纯函数模块**必须有单测**才允许进入下一阶段:

| 模块             | 必测用例                                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| `parser.ts`    | ① 纯 JSON ② \`\`\`json 代码块包裹 ③ 前后带废话文本 ④ 半截 JSON(流中断) ⑤ 字段缺失/类型错误(zod 拦截) ⑥ 空 action                             |
| `scheduler.ts` | ① 线性图拓扑序 ② 菱形汇合图 ③ 简单环/自环(抛 CycleError 且错误信息含节点名) ④ condition 剪枝(true/false 双分支) ⑤ 多个 start / 零 start 校验 ⑥ 孤立节点 |
| `template.ts`  | ① 简单替换 ② 深度路径 `a.b.0.c` ③ 未定义变量报错信息准确 ④ `{{}}` 空引用 ⑤ 模板内多个引用 ⑥ 值含特殊字符不二次解析                                      |

单测文件放 `engine/__tests__/`(完整路径 `src/renderer/src/pages/workflows/engine/__tests__/*.test.ts`)。已验证 `vitest.config.ts` renderer project 的 include 为 `src/renderer/**/__tests__/**/*.{test,spec}.{ts,tsx}`,该路径自动收录。命令:`pnpm test:renderer -- workflows`。调度器与解析器的 bug 在单测里修的成本,是画布上调修的十分之一。

## 十三、AI 协作开发守则(固定套路,每阶段执行)

1. 每个阶段先立验收标准,再动手;
2. 一次只让 AI 改一个模块,改完立刻 `pnpm dev` 目测 + `pnpm typecheck`;
3. 遇到报错 → 把完整报错原文(不翻译不总结)贴回给 AI;
4. 每完成一个阶段 `git commit` 打存档点,出问题随时回滚;
5. TypeScript 报错 = 免费向导,禁止 `@ts-ignore` 跳过(尤其 `SidebarIconsManager` 的 `satisfies` 约束会主动拦截遗漏);
6. 改 `databases/index.ts` 前先备份 IndexedDB 目录;
7. **架构决策必须人把关**——尤其阶段 3 调度器(AI 最容易写出死循环/剪枝漏洞的地方)与阶段 2 协议 schema。
