# Cherry-Studio-BB v1.11.2 Release Notes

## 🎯 核心主题：语音输入法体验修复 —— 不再吞字、不再卡顿、音频流更干净

这一版修的是「语音输入法」这条链路上长期别扭的地方，**属于修复与打磨**：不新增任何依赖、不改数据库结构、用户数据完全兼容。

**先说主人最有感的那一条**：按住快捷键说话时，程序注入的「退格」在目标程序里其实是 **「Ctrl+退格 = 删掉一整个词」**。默认快捷键就是 `Ctrl + \``，而"按住说话"意味着整个录音期间 Ctrl 一直是物理按下的 —— 于是退格变成了按词删除，而打字器还按"一次退格删一个字符"算账，**一错位就把已经上屏的正确内容一起吃掉**，并且它自己以为打对了，这一轮后面全部跟着错。

为什么之前"感觉不对劲但说不清"：**纯中文时看着正常**（ICU 把每个汉字当一个词，Ctrl+退格 ≈ 普通退格，运气好），一旦出现英文、数字、中英混排就开始吞字。现在注入前会先查物理按住的修饰键、在**同一次按键注入里**先补一条「抬起」记录，退格回到"删一个字符"的正常语义。

**第二件：腾讯云那家的结束报文写错了（硬伤）。** 官方要求上传完音频后发 `{"type": "end"}`，代码发的是 `{"end": true}` —— 服务端会当作未知文本消息（错误码 4010）直接断连。表现是：每次松手要等 5 秒超时才出结果、偶尔弹一个"请检查密钥与网络"的假警报、**已经上屏的最后一句还可能被回滚删掉**。现已按官方报文修正，并把异常路径统一改成"绝不把已经显示出来的文字删掉"。

**第三件：卡，是界面线程被自己堵住了。** 三条原因叠在一起还会互相放大：

- 音频采集用的是**被官方废弃的 `ScriptProcessorNode`** —— 它的回调跑在界面主线程上，主线程一忙音频就掉块；
- 输入框**每打一个字都要重测一次高度**（实测每字 **1.4 次样式计算 + 2.4 次强制重新排版**），一次识别结果吐几个字就是十几次重排；
- 主进程**每 500 毫秒给剪贴板图片做一次 PNG 编码 + MD5**，而"变没变"的判断还排在这一切之后，等于白算 —— 主进程同时还负责转发语音音频、注入按键，被占住就一起顿。

于是形成死循环：卡顿 → 音频掉块 → 识别变差 → 服务端改写 → 更多退格重打 → 更卡。三条现在都在各自源头修掉了：采集换到**音频线程**、注入期间关掉自动高度、剪贴板先用系统序列号当"变化闸门"。

**顺带修掉一个会让麦克风常开、越用越卡的问题**：快速连按（上次的麦克风还没打开就又按了一次）时，旧实现会同时建起**两条录音链路**，第一条永远没人停 —— 麦克风指示灯常亮、CPU 越用越高、同一句话被推两份给识别服务。

## 🧹 本次改动

### 1. 修复：退格被当成「Ctrl+退格 = 删一个词」

- 注入前用 `GetAsyncKeyState` 查物理按住的修饰键（左右 Ctrl / Shift / Alt / Win），**在同一次注入批里先补一条抬起记录**：目标程序处理退格时看到的就是"修饰键已松开"
- 只松开、不还原 —— 还原会往注入序列里再插一对按下/抬起，反而让目标程序看到自相矛盾的键盘状态
- 新增**精确回声登记表**：自己注入过哪些键码就登记几条，超时作废；**注入的修饰键抬起必须被"按住检测"忽略**，否则录音会被自己的注入判成"主人松手"而中途停止

### 2. 修复：腾讯云实时识别的结束报文

- `{"end":true}` → 官方原文 **`{"type":"end"}`**
- 异常路径（服务端报错 / 连接断开 / 收尾超时）改为返回**已经上屏的文本**，不再返回更短的"稳态文本"（那会让打字器把主人已经看到的那句话退格删掉）
- 顺带修掉一条把错误报文锁死的单元测试

### 3. 修复：快速连按导致麦克风泄漏 + 双路串音

- 竞态开关由布尔改成**轮次编号**（开始 +1、结束也 +1），麦克风与录音链路两处异步返回后都核对轮次
- 被取代的那一轮立刻释放麦克风与音频上下文；任何一步失败也回收"拿到一半"的资源

### 4. 改进：语音注入期间关掉输入框自动高度

- 受控输入框每变一次值，组件都要重新测量内容高度（强制同步重排）。注入期间不再测，识别结果一次吐几个字也不会把界面堵住
- 终态（完成/出错）才恢复自动增高 —— 松手后还要上屏最终校正，那期间同样不能打开

### 5. 改进：音频采集从 `ScriptProcessorNode` 换成 `AudioWorklet`

- 采集处理跑在**音频线程**：主线程忙的时候音频只会排队，不会丢
- **拿不到就自动退回老方案**（保证不会因为新方案挂掉就录不了音）
- 重采样、分包这些算法仍留在可测试的主线程代码里

### 6. 改进：降采样加了抗混叠滤波

- 旧实现 48k→16k 只是三点平均：**超过 8kHz 的分量不会被滤掉，而是折叠回可听频段**（实测 10kHz 还能漏进 48.9%），同时 6kHz 的齿音被削掉 20%
- 改为先跑 41 抽头汉明窗低通再取样。实测：10kHz 残留降到 15% 以下，1kHz / 3kHz 保持 90% 以上、6kHz 回到 85% 以上
- 踩坑记录：滤波与三点平均**不能叠加**（平均本身也是低通），否则 6kHz 会被二次削掉 —— 这一点是被单元测试挡下来的

### 7. 改进：剪贴板轮询加了前置闸门

- 用 Windows 的剪贴板序列号在**昂贵读取之前**判断"到底变没变"，没变就整轮跳过
- 读不到序列号时（FFI 不可用 / 调用异常）**自动退回原来的逐格式读取**，功能不受影响

### 8. 新增：语音输入耗时埋点

- 每次说完会打一行日志：`按下→首块音频 xx ms；按下→首次识别 xx ms；松手→最终文本 xx ms`
- 用途：判断"说快了开头几个字会丢"是不是麦克风启动慢造成的。**是否把麦克风预热常开，需要主人先跑一次、把数字发回来再决定** —— 预热能让开头不丢字，但代价是麦克风指示灯一直亮着，这属于隐私取舍，不替主人做主

### 9. 代码审查中发现并修掉的 3 个隐患

- 焦点守卫的回声计数会因为判断顺序而残留，最终可能吞掉主人真实的按键
- 录音失败的处理里会把"新一轮"刚建好的链路引用清掉，导致那条链路的麦克风永远没人释放
- 麦克风已拿到、但音频上下文建不起来时没有回收设备

### 10. 构建期抓到一个"会白装"的坑（单测发现不了）

- 新版采集处理器第一版放在源码目录里 import。跑一次构建后检查产物发现：构建工具把小于 4KB 的资源**内联成了 `data:` 形式的代码**，而主窗口的安全策略只允许同源脚本 —— **会被直接拦掉**，采集器加载失败、静默退回老方案，而且一点报错线索都没有
- 修法：把处理器文件放进静态资源目录（原样拷贝、不打成内联），运行时用同源路径加载。**没有削弱任何安全策略，也没有加构建配置特例**
- 已用构建产物验证：文件真实存在、产物里不再有内联形式、编译结果就是同源路径；并加了一条单元测试守住这个约束
